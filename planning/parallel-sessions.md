# Parallel Claude Code sessions (lanes)

**An Orchestrator, 5 Mains × lanes A–D** (RP-602). The **Orchestrator** decides which Main grills which epic and keeps the rules; each **Main** is a planning session for its epics, with four implementing **lanes, A–D**. Each implementing session works on **one ticket** in its **own app-made worktree**, so the desktop app binds its PR and sends CI / PR notifications.

| Session | Job | `pnpm lane:env N` | Jira label | Web |
|---|---|---|---|---|
| **Orchestrator** | Assigns epics to Mains, keeps the rule files, settles claims between Mains, housekeeping ("How the Orchestrator works"). No lanes; never grills a product epic. | `0`, only if it runs the app | — | localhost:3000 |
| **Main m** (m = 1–5) | Planning only: grilling, `/to-spec`, `/to-tickets`, reviews, questions, design prompts, for the epics labelled `main-m`. It edits docs in its own worktree, never in the main folder ("How a Main works"). | `m0` (only to run the app) | — | lane`m0`.localhost:3`m`00 |
| **Main m, lane A** | Implements Main m's tickets labelled `lane-ma` | `m1` | `lane-ma` | lane`m1`.localhost:3`m`10 |
| **Main m, lane B** | … labelled `lane-mb` | `m2` | `lane-mb` | lane`m2`.localhost:3`m`20 |
| **Main m, lane C** | … labelled `lane-mc` | `m3` | `lane-mc` | lane`m3`.localhost:3`m`30 |
| **Main m, lane D** | … labelled `lane-md` | `m4` | `lane-md` | lane`m4`.localhost:3`m`40 |

So Main 3's lane B runs `pnpm lane:env 32`, takes tickets labelled `lane-3b`, and opens `lane32.localhost:3320`. The labels run `lane-1a` … `lane-5d`, one per Main and lane. Lane `m0` has the ports the single-digit lane `m` had, so a Main keeps its stack; the other single-digit lanes (1–9) still work until no worktree uses them, but start new lanes only on `mL` numbers. Each lane has its own ports, database and Docker Compose project: see "Several worktrees at once" in the README.

**Capacity** (measured 2026-10-16, RP-613): 20 lane stacks (60 containers) started at once all came up healthy and used about 3 GB of Docker's 15 GB; no lane port is in a range Windows reserves (`netsh interface ipv4 show excludedportrange protocol=tcp`); the pnpm store is on G:, so a worktree's `node_modules` are hard links. What runs out first is the host's 32 GB, under the dev servers and test runs of 20 sessions: start a lane's containers and servers only while it works, and stop them when it is done (`pnpm servers:stop`). `pnpm storybook` asks for port 6006 and, with `--ci`, takes the next free one when another lane holds it (without `--ci` it asked whether to move, got no answer from an agent's shell and exited without starting): read the port it prints.

**Epics per Main.** The Orchestrator assigns each epic to a Main by labelling the Epic `main-1` … `main-5` (`project = RP AND issuetype = Epic AND labels = main-3`): e.g. Packages to Main 1, the next to Main 2. A Main works only on its own epics, takes each from grilling to spec to tickets, and labels the tickets `lane-ma` … `lane-md` with its own number, never another Main's. All five Mains work alike, and each implements through its own lanes.

**Shared modules are claimed across Mains** (rule 12): before a Main's lane changes a shared module (the list is in `docs/agents/issue-tracker.md`, "Ticket: shared files"), it comments `CLAIM <files> — Main m, lane-mx, RP-nnn` on the standing **Shared module claims** issue, RP-603, and `RELEASE <files> — RP-nnn (PR #n)` when the PR merges. Read the open claims first: a module another Main has claimed waits, or the two Mains agree there who goes first and the second merges `main` before its PR.

**Which ticket is next** comes from Jira, not this file: a lane's frontier is its `lane-mx` tickets that are `ready-for-agent` and have every "Blocks" blocker Done, and that are not In Progress (an implementer claims a ticket by moving it to In Progress and assigning itself: `docs/agents/issue-tracker.md`, Claim). The ticket gives a suggested model (Opus or Sonnet). To list a lane's open tickets (here Main 3's lane B):

```
project = RP AND labels = lane-3b AND labels = ready-for-agent AND statusCategory != Done AND status != "In Progress" ORDER BY rank
```

A lane takes work in one of two ways: **one ticket per session** (below), or **a whole spec in one session** with `/implement-spec`.

## How a Main works

Every session, Mains and lanes alike, reads `main` and merges into `main`. A Main's job is to get its decisions onto `main` before its lanes build on them, so a lane never reads a decision from another branch (RP-532).

1. **Start.** A new session on `G:\Rabaed Contech` named `Main m`. Before the first edit of a topic, call `EnterWorktree` named after it (`main-3-packages`), and keep the branch it makes (`worktree-main-3-packages`): no issue key in a decisions branch's name, since `jira-close` closes every key the merged branch names, the Epic too. Name the Epic in the PR body without `Closes`. A PreToolUse hook (`scripts/main-folder-guard.ts`) refuses Edit and Write in the main checkout outside `.claude/` (on 2026-10-16 a Main left an uncommitted `GLOSSARY.md` change there that no branch held, RP-613). `pnpm lane:env m0 --force` only when the Main runs the app.
2. **Grill**, with `/mattpocock-skills:grill-with-docs`, on an epic labelled `main-m`. The decisions go into that worktree: a new ADR in `docs/adr/`, `GLOSSARY.md`, design prompts in `design/prompts/`. Never the engine docs (`docs/data-model.md`, `workflow-engine.md`, `form-engine.md`, `visibility.md`): the building PR writes those (rule 9.2).
   - **ADR number:** `git fetch origin`, then the next number after the highest in `origin/main`'s `docs/adr/`. Two Mains can take the same one, and git merges two files `0023-…` without a conflict, so the unit test `scripts/docs-unique.test.ts` fails on a shared number; the PR the queue tests second then takes the next free number and updates its links (grep for the file name and `ADR 00nn`).
   - **Glossary:** each term defined once (the same test). A new _Avoid_ entry runs `pnpm lint` first (`docs/agents/issue-tracker.md`, "Spec: glossary").
   - **A Module that mirrors one we have:** when the epic adds a Module, Type or page that resembles an existing one, the first round asks, for each of outcome, Stages, pages, Form and actions, whether it is the same as the existing one or different, and proposes "the same" unless the owner names a difference. The Inspections grilling gave a WIR its own outcome and Stages; two days later the owner said a WIR is "just another Form", ADR 0025 replaced both, and it cost RP-673, RP-674, a WIR Workflow Version 3 and a Stage migration under live items (RP-1013).
3. **Decisions PR.** Open a docs-only PR from that branch as soon as the grilling ends, and queue it: `pnpm queue <number> --no-review --wait` (with RP-606 on `main`, label it `docs-only` first: every file it changes is a `.md`). Add the spec's migration days to `planning/migration-days.md` in the same PR or one like it, so the other Mains see them on `main`. These are placeholder days that keep the spec's own tickets apart; the final block is reserved just before the integration PR queues ("A whole spec in one session", step 4.5, RP-675).
4. **Spec and tickets** only after the decisions PR has merged: `/to-spec` and `/to-tickets`, pointing at `main`'s paths, never a branch (`docs/agents/issue-tracker.md`, "Specs"). Label the tickets `lane-ma` … `lane-md`; a ticket that changes a shared module names it, and its lane claims it on RP-603 (rule 12).
5. **Lanes** start from `origin/main` and merge `main` when it moves (rule 6), so they always read the latest decisions. Every lane builds through `/mattpocock-skills:implement` (one ticket) or `/mattpocock-skills:implement-spec` (a whole spec), never by hand (rule 15).
6. **Reading files.** A Main reads a repo file as `git show origin/main:<path>` after `git fetch`, or from its own worktree freshly cut from `origin/main`, never from the main folder's working copy: nobody updates the main folder, so it lags `main` (Main 4 nearly sent the owner an `inspection-on-phone.md` two PRs out of date; RP-1014).
7. **Rule files.** A Main never edits `CODING_STANDARDS.md`, this file or `docs/agents/*`: it files a Task under RP-567 and the Orchestrator makes the change.
8. **Retro on the Main** when a group of its specs and tickets is finished (every ticket merged and the epic review done): `/mattpocock-skills:retro` in the Main session itself, over the whole run from grilling to the last merge, not only the lanes' own retros (rule 16). The owner types the command (it must start the message, and an agent cannot load it itself).

## How the Orchestrator works

One session named `Orchestrator`, in its own worktree (`EnterWorktree` named `orchestrator-<topic>`), never the main folder. It has no lanes and never grills a product epic or writes a spec.

1. **Assigns epics.** The owner says which Main grills which epic; the Orchestrator labels the Epic `main-m` and moves it when the owner reassigns it. A Main whose epic is done gets its next one here.
2. **Keeps the rule files:** `CODING_STANDARDS.md`, this file and `docs/agents/*`, in docs-only PRs of its own (label `docs-only`, `pnpm queue <number> --no-review`). It owns the standing epic RP-567 (Agent tooling & retro): it files the retro and tooling Tasks there and hands RP-567 to a Main with room like any other epic, whose lanes build them.
3. **Settles claims between Mains** on RP-603 when two Mains need the same shared module (rule 12), and decides who merges first.
4. **Housekeeping**, from its own worktree (the prune never removes the stack of the folder it runs in): `pnpm worktrees:prune`, `pnpm lanes:prune`, archiving finished sessions, checking that the lanes' ports and stacks are free.

## How to start every implementing ticket

1. In the Claude desktop app → Code tab → **new session** on `G:\Rabaed Contech` with the **worktree** option on (the app creates the worktree and branch). Never start an implementing session in the main folder, and never run `git worktree add` by hand for it — the app wouldn't see the PR.
   **Session already open on the main folder?** Keep it and recover in place, in this order. The rule above still holds: nothing is implemented in the main folder.
   1. Call the `EnterWorktree` tool, named after the branch. It creates `.claude/worktrees/<name>` from `origin/main`, but if a worktree of that name already exists it **resumes** it (once it resumed another session's live one). Check the worktree is yours before working in it: `pnpm lane:env` refuses a worktree another live session holds (RP-501's lock check); if it does, stop and use another name.
   2. Rename the branch to the key's name (`git branch -m RP-nnn-...`), then run `pnpm lane:env N --force`.
   3. After `gh pr create`, link the PR to the session with `bind_pr`, so CI and Auto-fix notifications still arrive.
2. Name it `Main m, lane X – RP-nnn`.
3. First message (`mL` is the lane's number, e.g. 32), starting with the slash command: the app loads a skill only from a command at the very start of a message, and `implement`, `implement-spec`, `to-spec`, `to-tickets`, `grill-with-docs` and `retro` are skills an agent cannot load itself (their `disable-model-invocation`), so a command later in the message is just text:
   ```
   /mattpocock-skills:implement RP-nnn. Main m, lane X: first run `pnpm lane:env mL --force`.
   ```
   `lane:env` refuses a lane whose ports are taken, or whose compose project (`rabaed-laneN`) another worktree still uses, and names the container holding it. It also refuses a number that is not a lane (15, 55, 60, …). Add `--free` to take the next free lane instead (the same Main's lanes first), or run `pnpm lanes:prune` (below) first. If the ticket changes a shared module, claim it on RP-603 first (rule 12).
   **A UI ticket is shot before its review** (RP-533), and `/implement`'s `/code-review` runs before the PR opens, so do it inside `/implement`, in this order:
   1. With the app running on the lane (`pnpm demo`), run `pnpm screens <route>... --as <person>` (`scripts/screens.ts`, RP-531: full-page, 1366 and 1920, English and Arabic) for every page the ticket names. `--setup <file>` creates or moves the items first and fills `{id}` in the routes. The PNGs land in `.screens/<issue key>/`.
   2. Give the Spec reviewer those PNG paths with the ticket's reference screen in `design/reference/claude-design/` (or the design request it waits for), to compare them.
   3. Fix what the review finds, and shoot the pages the fixes changed again for a second look.
   4. Shoot every page the ticket names once more with `--publish`, and put the table it prints in the PR body (`CODING_STANDARDS.md` › UI).

   On spec RP-511 the shots came after the review, and no reviewer saw that RP-513's "With" line (who holds the item now) sat at the end of the page instead of in the header the reference shows.
4. When the PR opens, it appears in that session's PR bar: turn on **Auto-fix**. CI failures, merge conflicts and review comments will wake that session. To read a failed job's log without waiting for the rest of the run, see `docs/agents/ci-logs.md`.
   Once CI is green and `/code-review` is done, the session queues its own PR; nobody merges by hand. "Done" means its fixes are pushed and the PR carries the **`reviewed`** label: the reviewer adds it as its last step (`gh pr edit <number> --add-label reviewed`), and `pnpm queue` refuses a PR without it (`--no-review` skips the check for a docs-only PR and says so; RP-584). The `reviewed-label` workflow (PR #221) removes the label on every later push, so it always means "reviewed at this head", and `pnpm queue` also needs a finished run of that workflow on the PR's head (it refuses while one is running or failed; the workflow also runs when a PR opens or reopens, so a PR never pushed to after opening has one too, RP-604): add the label only after the last push's run has finished, and add it again after a push that removed it. Fork PRs are not handled (the job skips them). A push that only merges `main` in by a clean automatic merge (second parent already on `main`, tree identical to `git merge-tree` of the two, no edit of its own) keeps it, while a conflict resolution or any other change removes it and the review runs again. `gh pr merge` cannot queue it: it tries to turn on auto-merge, which this repository does not allow ("Auto merge is not allowed for this repository"). Queue it with one plain command:
   ```
   pnpm queue <number> --wait
   ```
   It works from any checkout (the main folder, another worktree, a lane): it fetches `origin/main` and the PR's own head (`refs/pull/<number>/head`), and refuses, with the fix, when the PR conflicts with `main` or when a migration shares a timestamp with (or sorts before) one on `main`, all checked on the PR's head, not on HEAD (a warning only, when HEAD is on the PR's branch but behind it); then it queues the PR through the API pinned to `expectedHeadOid` = the PR's head, and prints the position and state. `--wait` then polls every 60 s and exits 0 when the PR merges, or exits 1 with the removal reason when it leaves the queue (or closes). Leave `--wait` off to queue and move on. The raw `enqueuePullRequest` GraphQL call is the fallback only when `pnpm queue` itself cannot run; it skips those checks. (PR #149's CI was green hours before it was queued, and `main` had moved: the queue removed it five times.) `expectedHeadOid` is the commit CI passed on: if the branch has moved since, GitHub refuses to queue it. The merge queue tests the PR on top of the PRs queued ahead of it and merges it only when that run is green, so two PRs that are green alone cannot break `main` together. The queue does not resolve text conflicts, and a PR it removes leaves the queue with its own checks still green. When the queue removes a PR for a failed check, the `queue-drop-comment` workflow comments on the PR with the removal reason and each failing job of the queue's run with up to two lines before its first `##[error]` line (RP-401); that comment is what wakes the session's Auto-fix. A PR removed for a conflict shows the conflict on the PR itself, which Auto-fix watches (GitHub does not run `pull_request` workflows while a PR has a merge conflict, so that comment may never post). A PR a person took out of the queue on purpose gets no comment. The session then merges `main`, pushes and queues the PR again.
5. After the queue merges the PR, run `pnpm worktrees:prune` (see "Pruning old lanes"), then `/mattpocock-skills:retro` in that session (see below), then archive it. The next ticket gets a fresh session (this replaces `/clear`).

## Pruning old lanes

Never run `docker compose down -v` (or `--volumes`, or `docker volume rm rabaed-*`) by hand: it deletes a lane's database volume, and the committed `.claude/settings.json` denies those commands for agents. Free a lane only with `pnpm lanes:prune --lane N` (or `pnpm worktrees:prune` after merges), which confirm first and keep a live worktree's lane.

Every worktree that ran `pnpm dev` leaves a `rabaed-*` Docker Compose project behind (its containers, database volume and network), holding its lane's ports. `pnpm lanes:prune` lists those whose worktree no longer exists, that are not running, or that only have volumes left, and removes them with their volumes after you confirm (`--yes` skips the prompt). It never removes the current worktree's project. The Orchestrator runs it after archiving finished sessions, or in a lane when `lane:env` says a lane is taken. `lane:env` says whether the worktree holding the lane is on a branch (or a detached HEAD) already merged into `origin/main`; then `pnpm lanes:prune --merged` also removes the projects of such worktrees, unless a worktree that is not merged names the project in its `.env`. Add `--lane N` (`pnpm lanes:prune --merged --lane 32`) to free only `rabaed-lane32`, with the same confirmation and keep rules; `lane:env` suggests exactly that, so never reach other lanes' databases with a bare `--merged` or a raw `docker compose down`. `pnpm lanes:prune --dry-run` (also with `--merged` or `--lane N`) only lists what it would remove, exits 0 and never prompts or removes.

A lane's `db`, `mailpit` and `files` containers run with `init: true` (RP-983), so a container whose child processes have exited still stops and is removed. Restarting Docker Desktop is the fallback only, when a prune still fails with "PID … is zombie and can not be killed" (a stack started before RP-983, such as lanes 41, 43 and 44 on 2026-10-19): it stops every Main's running containers, so the Orchestrator does it once, at a quiet moment, then reruns `pnpm lanes:prune --merged --lane N --yes` for each stuck lane.

`pnpm lane:env N --force` does not need a prune to take lane N over from a worktree that is gone, or whose branch is merged into `origin/main` (on a detached HEAD: whose HEAD commit is in `origin/main`, RP-601) and has no uncommitted changes (RP-500): it removes that project's containers, keeps its volumes (the database), and says which worktree it came from; the next `docker compose up` recreates the containers under the new worktree. A holder that is not merged, has uncommitted changes, is locked by a session that still runs, or is a folder git does not list still refuses, as does a not-merged worktree that has the project in its `.env`. A `--db` run never takes a lane over.

`pnpm worktrees:prune` does the whole clean-up after merges. After `git fetch --prune origin` it lists, and after you confirm (`--yes` skips the prompt) removes:

1. Every worktree merged into `origin/main`, or whose upstream branch is gone, with its compose project, its folder and its branch. Desktop-app worktrees under `.claude/worktrees/` go only when merged into `origin/main`.
2. Every other local branch merged into `origin/main` and checked out in no worktree. It checks with `merge-base --is-ancestor origin/main`, not `git branch -d`, and never deletes `main`.
3. The orphaned compose projects `lanes:prune` finds.

It never touches the main checkout or the current worktree. It skips, and lists, worktrees with uncommitted changes (untracked files outside ignored paths included), commits on no origin branch, a lock by hand, or an open Claude desktop session. A compose project that a kept worktree names in its `.env` stays.

**Held worktrees** (RP-956, RP-612): `worktrees:prune`, `worktrees:clean`, `lanes:prune --merged` and `lane:env --force` never remove or take over a worktree a running Claude session is in (its cwd, from `~/.claude/sessions/<pid>.json`, `EnterWorktree` and CLI sessions included) or an open desktop session holds, and they name that session. If the sessions can't be checked, every worktree is skipped. So a Main's own `main-*` worktree and the Orchestrator's are safe while their session runs, and `--yes` is fine again. Until RP-1007 lands, one gap remains: `lanes:prune` can still remove a "volumes only" lane (and `lane:env --free` hand it out) that a live worktree's `.env` names; before pruning a lane by number, check no open session's `.env` names it.

**Finished worktree** (RP-585): `lane:env`, `lanes:prune --merged`, `worktrees:clean` and `worktrees:prune` judge "merged" by one rule (`scripts/worktrees.ts` `isFinished`). A worktree, on a branch or a detached HEAD (RP-601), is finished when its tip is in `origin/main` (or `--into`'s branch) and either its branch has had a commit of its own, or it has none and it is clean, its lock names no other running Claude session (the app locks a subagent's worktree with its parent's pid, so a session's own paused subagents do not hold it against that session), and no running process's command line names its folder; on a branch it also needs a lock naming a session that has stopped (RP-610): an unlocked branch never committed to may be a session that just branched off `origin/main`, so it is never finished (one was pruned minutes after `git switch -c`). A branch made on a merged tip and never committed to (a paused implementer's, under the app's agent lock) is so finished once its session is gone; `lane:env --force` then takes its lane over, saying why, without `lanes:prune`.

Under the skipped list, both `worktrees:prune` and `worktrees:clean` print a **Stale** section (RP-506): the skipped worktrees whose last commit and newest uncommitted file are both older than `--stale-days <n>` (default 7), oldest first, with the age in days, the branch, the skip reason and, when the lock names a pid, whether that process still runs. It only lists; nothing in it is removed, unlocked or changed. Decide on those by hand (a lock whose pid is not running is a leftover of a closed session).

## A whole spec in one session (`/implement-spec`)

Use it when a spec's tickets form a chain that one lane would otherwise work through one session at a time (e.g. RP-290 → RP-294 under spec RP-289). Implementer subagents build the ready tickets in parallel, each in its own worktree, and merge them onto one **integration branch**; one `/code-review` runs over the whole branch at the end, which counts as the spec's epic review.

1. Start the session as in step 1 above, named `Main m, lane X – RP-nnn (spec)`, with the spec's key. First move the spec issue to **In Progress**; if it already is In Progress, another session owns it: stop. `pnpm lane:env` also refuses a worktree locked by another live `claude session`, even with `--force` (RP-461 was run by two sessions at once).
2. First message:
   ```
   /mattpocock-skills:implement-spec RP-nnn. Main m, lane X: first run `pnpm lane:env mL --force`. Name the integration branch RP-nnn-<spec-name> and open its draft PR after the first merge.
   ```
3. Label every ticket of the spec with this lane, so no other lane starts one of them. A ticket marked **own PR** (it changes root `package.json`, `pnpm-lock.yaml` or `.github/workflows/*`; rule 3) is not merged onto the integration branch: its implementer subagent branches from `origin/main`, and it goes up as a PR of its own (RP-331 had to be reverted off spec RP-327's branch and split into PR #130).
4. The subagents share the lane's Postgres, but each uses its own databases. Before launching them, and after any long pause, run `docker compose ps` in the session's own worktree and start any container of the lane that isn't up from there: `docker compose up -d --wait db mailpit files` (RP-575: lane 8's containers were down for a whole round, found only at `test:seam1`). `pnpm verify` also stops before its first step when the lane's Postgres doesn't answer.
   1. In its worktree, each implementer subagent first checks that HEAD is the integration branch's tip, and runs `git reset --hard <sha>` if it isn't, where `<sha>` is the integration tip the brief gives as a SHA (`git reset --hard 3f2a91c0e`), never the branch name: a worktree-isolated subagent starts from `origin/main` (two of seven did on spec RP-361), and a branch name can point at an older tip than the session's unpushed one (RP-960 built on a stale tip; RP-1021). If the ticket's branch already exists, it stops and reports the worktree it is checked out in (`git worktree list`): a taken branch means another implementer has the ticket (on spec RP-461 one implementer built `RP-451-...-2` beside another session's). Otherwise it branches `RP-nnn-...` from there and runs `pnpm lane:env N --force --db rp<n>` (`<n>` is its ticket number, e.g. `--db rp322`). The three database URLs then name `rabaed_rp<n>`, so its seam suites use `rabaed_rp<n>_test`, and parallel seam suites never migrate the same database.
   2. `lane:env` still refuses a lane whose ports are taken, but a `--db` run in a second worktree of the same lane is allowed. `--db` is only for the implementer subagents of the session that owns the lane. A session whose lane is held by another session's worktree never shares it with `--db`: it takes a free lane (`--free`) or frees one with `pnpm lanes:prune` (RP-334's session was stopped sharing RP-337's lane). Don't run `pnpm demo` or `pnpm dev` on the lane while implementers run `lane:env --db`: its api port is then held and every `--db` run refuses; start it after they finish, or on another lane (RP-545). `lane:env` names a server of the session's own when it finds one.
   3. Each seam run recreates its `_test` database itself. A second seam run on the same database while one is going refuses with a message; let the first finish.
   4. When the spec is done, run `pnpm lanes:drop-dbs --lane N` (your lane) to list and drop the `rabaed_*` databases of worktrees that no longer exist in that lane's Postgres (`--yes` skips the prompt). It checks only this clone's worktrees, and keeps any database something is connected to. Without `--lane` it looks at every lane's Postgres, so another session's databases on another lane would be listed too (RP-535).
   5. Migration timestamps: each ticket gets its own day, in the order of the spec's tickets (the first ticket takes `<yyyymmdd>xxxxxx`, the next the following day, and so on), and its migrations use only that range, so parallel migrations never collide. Say the ranges in each subagent's brief. Migrations already on main stay unchanged.
      - The spec also reserves one more day, after its last ticket's, for the epic review's fixes (RP-363's review fixes had no day and took a timestamp main already held), and one for a merge-with-`main` reconciliation when a ticket redefines an `app.*` function (rule 11.1).
      - Specs that run at the same time get ranges that don't overlap: before handing out days, read `planning/migration-days.md` on `origin/main` and take the next free block after every day already reserved. The spec's Main writes the spec's days there (one table row per day: `| yyyymmdd | RP-nnn (or spec RP-nnn) | lane | purpose |`, columns Day, Issue or spec, Lane, Purpose) and merges them before the spec starts ("How a Main works", step 3); a reservation made only in a comment is invisible to other lanes (RP-525's `20270117`, taken on main, RP-560). That file is the only record: the spec's ticket table links its rows and has no days column of its own (RP-536). A lane that finds no reservation for its spec stops and asks the spec's Main.
      - **Placeholder days, then the final block** (RP-675). The block reserved at spec start is a placeholder: it keeps the spec's parallel tickets apart while they build. Any single ticket that merges meanwhile takes the first day after every reservation, so a spec that builds for days is always overtaken, whatever block it took (RP-616 moved twice, RP-631 eight times). So when the integration PR is ready to queue (every ticket merged, the whole-branch review's fixes pushed), merge `main`, then run `pnpm migrations:reday` on the integration branch and queue at once. Until then a "migrations immutable" or drift failure on the draft integration PR is expected, and no one moves days by hand.
      - When `main` overtakes a branch's migrations, run `pnpm migrations:reday` on the branch (after merging `main`): it moves them all past main's newest and every branch's reservations in one commit, keeping their order and bodies, rewrites references to the old names, swaps the branch's rows in `planning/migration-days.md` for rows on the new days (leaving no "Unused" row), then runs `pnpm check:migrations`. Never move migrations by hand-written scripts (RP-988).
      - `pnpm check:migrations` refuses a migration on a day that file reserves for another issue. A migration counts as its branch's issue's (`RP-nnn-…`) and the first issue key on its header comment's first line (later keys are mentions), so start each migration's header with its issue key (the spec's, for the review fixes).
      - A single ticket (no spec) creates each migration with `pnpm migration:new <name> --issue RP-nnn` (RP-583): after `git fetch origin` it takes the first day after every migration on `origin/main` and every remote branch (the queue's `gh-readonly-queue/*` too), every day this file reserves and every migration in the worktree, creates `packages/db/migrations/<day>000000_<name>.sql` with the issue key in its header, and adds the day's row (lane from `.env`) to `planning/migration-days.md`; commit both together. Hand-picked days were overtaken by `main` (PR #199 left the queue four times).
      - Before opening or updating a PR, run `pnpm check:migrations` (rule 10 below) to catch a shared timestamp locally.
5. When the last ticket is merged in, shoot the pages every UI ticket of the spec names before the whole-branch `/code-review`, and publish them all after its fixes are pushed, in the order step 3 of "How to start every implementing ticket" gives (RP-533). The integration PR stays a draft, with no `reviewed` label and no queue command handed to anyone, until the whole-branch review's fix commits are pushed and CI has run on them: lane 4D queued #327 and #329 while those fixes were still being written, the fixes touched all four tickets, and they needed a third PR (#333) after `jira-close` had already closed RP-977 and RP-979 (RP-1011). When that is done, add the `reviewed` label to the integration PR (`gh pr edit <number> --add-label reviewed`), mark it ready (`gh pr ready`) and queue it with `pnpm queue <number> --wait`, as in step 4 of "How to start every implementing ticket": the whole spec goes through the queue as one entry. When the PR merges, the `jira-close` workflow closes every ticket the branch name or a `Closes RP-a, RP-b` line in the PR body names (`docs/agents/issue-tracker.md`), so list each of the spec's tickets in the body.
6. Clean up the subagents' worktrees once the last subagent has finished.
   1. Run `pnpm worktrees:clean --into RP-nnn-<spec-name> --yes` (`--into main` once the PR has merged). It fetches origin first and checks against `origin/<branch>` when that exists, so `--into main` checks `origin/main` and a stale local `main` hides nothing (RP-564); it uses the local branch when that is ahead of origin's or origin has none, and prints the ref it used.
   2. It unlocks and removes every `.claude/worktrees/agent-*` worktree whose commits are all in that branch, with its leftover folder (Windows keeps `node_modules` behind). It lists each one's dev servers and stops them first, as `pnpm servers:stop` would (RP-568); a worktree whose server cannot be stopped is kept. It deletes each branch that is an ancestor of that branch with `git branch -D` (so `--into <integration branch>` works from the main folder, which has `main` checked out), plus the `worktree-agent-*` branch the app created the worktree on; a branch with commits not in the target is kept and named.
   3. It skips, and lists, worktrees with uncommitted changes or unmerged commits, and worktrees with no commits yet that a running session's lock or a running process (such as its dev server) still holds, since their subagent may still be running (another lane's, too: all lanes share `.claude/worktrees/agent-*`). `--include-empty` removes those with no commits yet anyway.
   4. Then run `/mattpocock-skills:retro` and archive the session.
   5. When you stop an implementer yourself, remove only its worktree: `pnpm worktrees:clean --only agent-<id> --yes` (several ids may follow `--only`). It removes the named worktree even with no commits, and leaves other sessions' worktrees unlooked at; hand-run `git worktree remove` and `git branch -D` are refused by auto mode.

## Implementer brief

Every implementing session and implementer subagent follows these, on top of the ticket and `CODING_STANDARDS.md`. An `/implement-spec` brief points here instead of repeating them.

- **Build only through the skill:** the session runs `/mattpocock-skills:implement` or `/mattpocock-skills:implement-spec`, whose steps include `/mattpocock-skills:tdd` (test first, one red-green slice at a time) and `/code-review` (Standards and Spec) before the PR is queued; it never writes the ticket's code outside them (rule 15).

- **Isolated worktree shell:** plain, literal commands that act on this worktree only; write scripts with Write and run them; no heredocs, `git -C`, `cd … &&` or variable paths. Run `pnpm lane:env` from PowerShell, not Git Bash.
- **Worktree gone under you:** if the main-folder guard refuses a git command because the worktree folder has no `.git`, stop: the worktree was removed under you. Never run git from that folder (git would act on the main checkout); report it and start a fresh worktree (RP-956).
- **Fresh worktree:** run `pnpm install --frozen-lockfile` first (a new worktree has no `node_modules`, so `vitest` is missing).
- **Glossary lint:** run `pnpm lint` before your first commit; scripts and `messages/*.json` are linted against `GLOSSARY.md` _Avoid_ too (`packages/eslint-plugin/README.md` lists the common false hits and how to silence one).
- **Jira comments:** a brief that cites a decision by comment ID means: read it with `listJiraIssueComments` on that issue (Atlassian MCP), newest first. There is no `getJiraIssueComment` (three implementers on spec RP-631 called it; RP-1021).
- **Long steps in the foreground:** run `pnpm verify` and the seam suites in the foreground, so their result ends your turn. A background run's notification is the signal: wait for it, never poll with `sleep`. On spec RP-631, background verify runs woke the integration session for about 25 no-op turns (RP-1021).
  - **A run longer than the tool's timeout:** run `pnpm -s verify --log verify.log` in the background (`*.log` is git-ignored). Everything goes to the file, every step's whole output too, and the terminal gets only verify's last line, so the notification's line and exit code are verify's own (`-s` keeps pnpm's own lines off the end). Never pipe verify through `tail` or `grep`, or end the command with `; echo verify $?`: the notification then reports the last command's exit code, not verify's. On spec RP-631 every such notification read "exit code 0", the failing run's too (RP-1019).
- **Report ends with the verify line:** the report ends with the last line of `pnpm verify`, verbatim (`pnpm verify passed on <sha>: <steps>.`), from one complete run on the pushed commit, or names the step it stopped at and why. A fix after the run means a new run.
  - **Resume after a late failure:** fix it and run `pnpm verify --from <step>` (`--from seam1`, the step's script name with or without `test:`/`check:`; an unknown name lists the steps), so the steps before it are not run again. Its last line starts `pnpm verify --from <step> passed` and names the steps it did not run; `pnpm queue` does not accept it, so the report's line still comes from one complete run on the pushed commit (RP-1019).
- **Renames:** renaming a term, label or message key, or removing a group, follows the checklist in `docs/agents/renames.md`.
- **Stories:** when the diff touches `packages/ui/`, `apps/web/` or any `*.stories.tsx`, run `pnpm test:stories` from the repo root before pushing (`pnpm verify` already includes it then). Off Linux it compares no screenshots, so any failure is a real behaviour or axe failure; screenshot baselines come from `pnpm test:stories:linux` or the `update-screenshots` label on CI. CI then pushes an "Update story screenshot baselines" commit to the branch, so after a UI change run `git pull --no-rebase` before the next push, or the push is rejected (RP-460).
- **Design docs:** don't read `docs/workflow-engine.md`, `docs/visibility.md`, `docs/form-engine.md` or `docs/data-model.md` whole (80–160 KB each). Each opens with a Contents list saying which part to read when. Find your heading with `grep -n '^#' docs/<doc>.md`, then Read from that line with offset and limit (RP-538).
- **Owner reference pages:** a page built from the owner's reference (the anatomy and design pages in `D:\Artifacts`) follows `design/owner-reference-process.md`: reference → screenshot every view → gap table → owner's answers → build → independent review → owner. Every gap-table row cites `<file> › <part>` (a CSS selector, `line N` or `screenshot N`), every rule-forced row quotes its ADR, `docs/visibility.md`, GLOSSARY or `CLAUDE.md` line, and `node scripts/check-gap-table.ts <table> --refs <folder>` passes. The independent reviewer opens every citation, not just the screenshots (RP-574: spec RP-528's table called a filled label "outlined" and read ADR 0017 as "no signatures").
- **Skill not in the session's list:** when a skill these docs name (such as `/mattpocock-skills:implement`, `/mattpocock-skills:implement-spec` or `/mattpocock-skills:retro`) is not among the skills the session may invoke (a Claude desktop session can leave plugin skills out of that list), read its `SKILL.md` from the plugin cache, `~/.claude/plugins/cache/mattpocock/mattpocock-skills/<version>/skills/engineering/<skill>/SKILL.md` (on Windows, `%USERPROFILE%\.claude\...`), and follow it, saying so in the report; or ask the user to type the slash command, which works even then (RP-609).
- **Last step: stop your dev servers.** Run `pnpm servers:stop --yes` in your worktree before you report (RP-568). It stops the node processes running from this worktree's `node_modules` (web, api, admin, Storybook), names their ports, and never touches another worktree's processes or Docker; `--dry-run` only lists, `--worktree <path>` names another worktree of this clone. `Stop-Process` and `taskkill` are refused by auto mode, so leave a server up only on purpose: RP-441's held lane 8 for nine hours. It is one plain command, so a permission rule can allow it: `"Bash(pnpm servers:stop:*)"` and `"PowerShell(pnpm servers:stop:*)"` in `permissions.allow`. `pnpm worktrees:clean` stops a worktree's servers before removing it.

## Retro before archiving

`/mattpocock-skills:retro` looks back at the session and suggests changes to the agents' environment, not the code. A mistake that a rule could catch becomes a check (a lint rule, a pre-commit hook or a CI job). A judgement call becomes a line in `CODING_STANDARDS.md`. Each accepted suggestion becomes a `ready-for-agent` Task, as RP-287 did. A new required CI check also has to be added to the `main` ruleset.

Retro Tasks go under RP-567, with the label `retro`, whichever Main's lane ran the session. Only the Orchestrator edits `CODING_STANDARDS.md` (rule 9 below). A Task that brings a standards line quotes the line; the lane builds only the check, and the Orchestrator adds the line, with its "(checked: …)" mark, in a docs-only PR once the check is on `main`.

## Epic review when a spec is finished

Every ticket already gets a `/code-review` inside `/implement`; when the review is done and its fixes are pushed, the reviewer adds the `reviewed` label to the PR (`gh pr edit <number> --add-label reviewed`, RP-584). When all of a spec's tickets are merged, one more review looks at the whole spec:

- Before the spec's first ticket, tag `main` as `epic-start/<name>`. When running `/to-tickets`, add a review ticket blocked by the spec's last tickets.
- The review runs in a fresh session with no worktree (it only reads): `/mattpocock-skills:code-review since tag epic-start/<name>, only <folders>, against spec RP-nnn`.
- Before filing, list the Epic's open tickets: `/implement-spec`'s own review files follow-ups there too (RP-383 repeated RP-336). A finding already filed gets a comment on that ticket; every other confirmed finding becomes a `ready-for-agent` Task under the same Epic, linked to the review ticket. Visibility and security findings are Highest.

## Rules that keep lanes from colliding

1. One ticket = one app-made worktree session = one branch named with the key (`RP-191-...`) = one PR. With `/implement-spec`, one spec = one session = one integration branch named with the spec's key = one PR.
2. Start only tickets whose blockers are Done.
3. When another lane's open ticket touches the same files (the ticket names them), keep your changes to those files in their own commits, and merge `main` right before opening the PR. Shared root files (root `package.json`, lockfile, CI workflows) change in small PRs of their own: `/to-tickets` marks such a ticket **own PR**, and inside a spec it is built from `main` (step 3 of "A whole spec in one session"). A dependencies-only PR (the lockfile plus the dependency fields of a workspace `package.json`, RP-573) also counts as such a PR.
4. Two lanes of one Main never run specs that change the same shared module at the same time, such as the work item query (`apps/api/src/work-items/query.ts`). Queue one spec behind the other, or give one of them only the UI. `/to-tickets` names the shared files each ticket touches, so the Main can see the overlap before it assigns lanes. Across Mains, rule 12's claims do the same. (RP-362 and RP-363 both reworked the query in parallel, and their merge had 10 conflicted files.)
5. Migrations are timestamp-named (and follow `CODING_STANDARDS.md`).
6. Merge only through the merge queue: queue a PR with green CI (both visibility suites must pass) and a finished `/code-review` (the PR has the `reviewed` label, which `pnpm queue` checks) with `pnpm queue <number>` (step 4 of "How to start every implementing ticket"; `gh pr merge` cannot queue). Merge `main` into your branch when it moves, and resolve any conflicts in that session. Before pushing the merge, run `pnpm lint && pnpm typecheck` and judge them by exit code, not by filtered output: a branch that adds or tightens a check re-checks the code `main` gained meanwhile, so fix what they find in the merge commit (RP-327's lint rule failed CI twice this way).
7. Parallel sessions multiply usage — close finished sessions.
8. A ticket whose spec is being built by `/implement-spec` (its lane label is set and its spec has an open integration PR) stays under that spec. If it must move, the spec's Main comments on the integration PR.
9. Docs have owners. Replaying the last 60 merges (2026-10-06), 9 of the 24 conflicted files were docs; the translation catalogues and the packages' `index.ts` files, though changed by nearly every PR, conflicted once or never.
   1. `CODING_STANDARDS.md`, this file and `docs/agents/*`: only the Orchestrator edits them (see "Retro before archiving" and "How the Orchestrator works"). `GLOSSARY.md`, `docs/adr/` and `planning/migration-days.md`: any Main, in a decisions PR.
   2. `docs/data-model.md`, `docs/workflow-engine.md`, `docs/form-engine.md`, `docs/visibility.md`: the lane writes them for what it builds, in the same PR. A grilling session records its decisions in a new ADR and in tickets, never in these files directly; a decision that builds nothing gets a small docs-only ticket.
   3. A new scenario in the `docs/visibility.md` matrix takes its ID from the ticket key (`RP-412-1`), never the next number (RP-397). When two branches add rows at the end of the table, keep both. When a merge stops on `docs/visibility.md`, run `node scripts/resolve-visibility.ts` in the merging worktree (RP-562): it merges rows the two sides changed apart (different rows, or the same row changed identically), and leaves git's markers, naming the row or line, on any row or line both sides changed differently; it never merges inside a row. Read the diff, then `git add` it.
   4. Add a new rule at the end of a numbered list; never renumber, since tickets cite rules by number.
10. Before opening or updating a PR that adds a migration, run `pnpm check:migrations`. It fetches `origin/main` and runs the drift check (redefinitions, stale overloads, shared timestamps) on `origin/main` and `HEAD`, the check CI runs, so a clash shows before the push (RP-363 learned of one only on merge). It also refuses a migration on a day `planning/migration-days.md` reserves for another issue, and warns of one on an unreserved day (step 4.5). It needs the network for the fetch. A pre-push hook is optional, not installed.
11. To change an `app.*` function, start from its newest body: `pnpm db:fn <name>` prints it with the migration and line (`--list` shows every redefinition). Do not grep the migrations for it; the first hit is rarely the current one.
    1. When `main` gains a redefinition of an `app.*` function your branch also redefines, rebuild yours in a new migration that sorts after both, starting from `main`'s body; editing your branch's migration in place still fails the drift check, which judges each branch migration by the commit that first added it. A later redefinition replaces every earlier one, so an unmerged ticket's redefinition then moves after it too (RP-449: `20270105000000_on_workflow_core.sql`, then WF-10's `20270105100000`; RP-460).
12. With 5 Mains, a lane that changes a shared module (the list is in `docs/agents/issue-tracker.md`, "Ticket: shared files") claims it first on RP-603, Shared module claims: `CLAIM <files> — Main m, lane-mx, RP-nnn`, then `RELEASE <files> — RP-nnn (PR #n)` when it merges. A module another Main holds waits for its release, or the two agree on that issue who merges first (RP-602).
    1. **`pnpm check:claims` enforces it** (RP-1008), in `pnpm verify` and the pre-push hook. It refuses a branch that changes a shared file or redefines an existing `app.*` function unless an open CLAIM on RP-603 names the branch's issue key, and it names the file and the CLAIM line to post. `pnpm claims --open` lists the open claims. Three things follow:
       - **The branch name starts with the key** (`RP-nnn-…`, rule 1). A branch named otherwise, such as the app's `claude/…`, is refused as soon as it changes a shared file: rename it first (`git branch -m RP-nnn-<slug>`). The rule files are on the shared list, so a docs-only branch that edits them needs its key and a CLAIM too, the Orchestrator's included.
       - **A RELEASE naming a key releases every claim under that key.** To release part of a claim, post the RELEASE, then CLAIM the rest again as a new comment (RP-603 comments 14463 and 14464 do this).
       - **No Jira token or no network:** it warns and passes, so a lane without `JIRA_EMAIL` and `JIRA_API_TOKEN` must still claim by hand.
13. Every slash command in `CLAUDE.md`, `README.md`, `planning/*.md` and `docs/agents/*.md` must name a skill in `.claude/skills/` or on the plugin allowlist `scripts/doc-skills.json` (`scripts/check-doc-skills.test.ts`, in `pnpm test:unit`; RP-609). The plugin cache is not on CI, so when the plugin is upgraded or a doc names a new plugin skill, refresh the allowlist from the cache's `skills/engineering/` folder; a slash word that is no skill (a built-in command, an app route) goes under `notSkills`.
14. The main ruleset requires the `reviewed-required` check (RP-606, `.github/workflows/reviewed-required.yml`): a PR merges with the `reviewed` label, or with the `docs-only` label when every file it changes is under `docs/` or a `.md` file. It runs on the PR and again in the merge queue, so a merge started from GitHub cannot skip the `/code-review` either. `pnpm queue` applies the same rule (`scripts/reviewed-required.ts`): a docs-only PR takes `gh pr edit <number> --add-label docs-only`, then `pnpm queue <number>` once the check is green. `--no-review` no longer skips the rule; without the `docs-only` label it refuses and says how to add it. The `docs-only` label stays across pushes (the check re-reads the changed files each run); a push that adds a code change fails it until the PR gets a review and the `reviewed` label. A PR opened before the workflow existed has no `reviewed-required` run, so the check stays pending until its next push or label change.
15. All implementation goes through `/mattpocock-skills:implement` (one ticket) or `/mattpocock-skills:implement-spec` (a whole spec), in every Main's lanes (owner's rule, 2026-10-19). Those skills drive `/mattpocock-skills:tdd` for each slice and run `/code-review` before the PR is queued, so every change is tested first and reviewed. A Main never builds a ticket itself, a lane never codes outside the skill, and a fix found after the review goes back through the same skill session. The lane's first message starts with the slash command ("How to start every implementing ticket", step 3).
16. Every Main, 1 to 5, runs `/mattpocock-skills:retro` in its own session each time a group of its specs and tickets is finished: every ticket merged, the epic review done (owner's rule, 2026-10-19). It looks back over the whole run, from the grilling and the decisions PR through the spec, the tickets, the lane plan, the shared-module claims and the merges, beside the retro each lane runs before it is archived. Its accepted suggestions become Tasks under RP-567 with the label `retro` ("Retro before archiving"); a rule-file line goes to the Orchestrator. The owner starts it by typing the command as the first thing in a message in that Main.
    1. **What the Main reads for it** (one retro over all its lanes, so nothing a lane learned is lost): (a) every lane session it started, archived ones included: `list_sessions` with `linked: true` and `include_archived: true`, then each lane's transcript with `list_events` (page back with `before_uuid`), above all the turns where a check failed, a push was refused, the queue dropped the PR or the lane asked for help; (b) every PR of the spec, merged and closed: `gh pr list --state all --search "RP-nnn"` for the spec and its tickets, with their failed checks, `queue-drop-comment` comments and Auto-fix events; (c) Jira: the spec and its tickets with their comments, the RP-603 claims of its lanes, and the Tasks its lanes already filed under RP-567 with label `retro` (`project = RP AND parent = RP-567 AND labels = retro AND created >= <spec start>`), so it adds to them instead of filing twice; (d) what Main 6 (review) and Main 7 (UAT) filed against the epic. A lane keeps its own retro before archiving; the Main's retro is the one that sees the patterns across lanes (the same failure in two lanes, a rule that slowed every lane).
17. Keep branches close to `main` (owner's rule, 2026-10-19). A ticket's PR is small: one ticket, one PR, queued the day its review is done; a ticket too big for a day is split with `/to-tickets` before it starts, not after. A branch open past one day merges `origin/main` into itself at least once a day, and again right before `pnpm queue`, then runs `pnpm check:migrations` and the checks the merge touched. A Main never lets a finished PR wait for a sibling: each one queues on its own. (2026-10-18 to 19: of 14 queue removals, 11 were a check that failed only on the PR merged with `main` and the PRs ahead of it, on branches 20 to 31 commits behind; PR #275 was removed three times.)
