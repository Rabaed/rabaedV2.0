# RP-1323 scenarios

Rows of the [scenario matrix](../../visibility.md#scenario-matrix-becomes-the-automated-visibility-test-suite) added under RP-1323 (the owner's decision of 2026-11-18, after [RP-1309](RP-1309.md): close the gap V20 named). `POST /v1/workflows/:w/duplicate` (into a Project, or into the Company's Library when no Project is given) and `POST /v1/workflows/:w/save-to-library` take as their source only a Workflow the Member reads through the Workflow's own reads (`GET /v1/workflows/:w`, `/map`, `/versions/:n`; RP-1309's rule). Any other source gets the 404 of a made-up id, with the same status and body, before anything is copied and before any later refusal (a closed Project) could tell them the id exists. The setup is Project "Tower": C1 the Host Company, whose Authorized Person created it and is its Project Admin; K1 its Consultant; a second Tower with its own Project Admin, which C1 joins, where C1's Authorized Person is a Project Member and not its Project Admin; and an Authorized Person on no Project. Each Tower's Project Admin has published a copy of MAR's Workflow that no Type runs.

The check is in the api, before `app.duplicate_workflow` (`readsWorkflowOffProject` in `apps/api/src/projects/workflow-settings.ts`), so the rule stays one: RP-1299's, as Project Settings lists it. Seam 1: `apps/api/test/rp-1323-visibility.test.ts`. Seam 2: `packages/db/test/rp-1323-visibility-rls.test.ts` pins down what the check reads as the app role (the Projects a Member is on, the bindings they read, the Projects they are a Project Admin of) and `app.duplicate_workflow`'s own bound, which still holds for any caller: a target they administer or their own Library, and a published source whose rows they read.
