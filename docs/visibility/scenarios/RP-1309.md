# RP-1309 scenarios

Rows of the [scenario matrix](../../visibility.md#scenario-matrix-becomes-the-automated-visibility-test-suite) added under RP-1309 (the owner's decision of 2026-11-14, after [RP-1299](RP-1299.md): the Workflow reads with no Project in their path hide a Workflow not in use from a Member who is not a Project Admin, as the Project's Settings pages do). The reads are `GET /v1/workflows/:w`, `GET /v1/workflows/:w/map` and `GET /v1/workflows/:w/versions/:n`, and every scenario checks all three. The setup is Project "Tower": C1 the Host Company, whose Project Admin created it; C1's engineer and PM; K1's manager; C2, a second Contractor, its Authorized Person and its engineer. There is also a second Tower with its own engineer, and a Member on no Project. Both Towers' MAR runs the same Rabaed Default submittal Workflow (RP-596).

The rule reuses RP-1299's: a Rabaed Default or a Project's Workflow is read only when Project Settings lists it to the Member on one of the Projects they are on. That is the one a Type runs or an exception's Workflow they read (V15), or, where they are a Project Admin, any Rabaed Default of its Types and any of its copies. A Company's Library Workflow is read by its own Members, as before (V18). Anyone else gets the 404 of a made-up id. Seam 1: `apps/api/test/rp-1309-visibility.test.ts`. Seam 2: `packages/db/test/rp-1309-visibility-rls.test.ts`. The filter is in the api read, so seam 2 pins down the row-level security it rests on: the Projects each reader is on, who is a Project Admin of which, the bindings, and a Project copy's rows and a Library Workflow's.
