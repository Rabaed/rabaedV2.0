# RP-1258 scenarios

Rows of the [scenario matrix](../../visibility.md#scenario-matrix-becomes-the-automated-visibility-test-suite) added under RP-1258 (a guard for V14 after RP-1139: default privileges grant each new table whole to the app role, so a new Member id column would be readable with nothing failing). No world is built: both seams read the live catalog.

| # | Scenario | Who | Expected |
|---|---|---|---|
| RP-1258-1 | Every Member id column the app role may SELECT: a column in `public` named `member_id` or `*_member_id`, or under a foreign key to `member(id)`, and `member.id`, granted whole or by column (`has_column_privilege`); and every view the app role may SELECT, whose columns carry no foreign key | The app role, as every Member reads through it; the role the api's pool logs in as | Each is on `MEMBER_ID_ALLOW` (`packages/db/test-support/member-id-grants.ts`) with the reason no other Company reads it (own Member's or own Participant's rows only, own Company's only, never set on a row anyone reads), and each entry still names one. A new readable Member id column or view fails until it is revoked or allowed with a reason; an entry that names nothing fails too. None of the columns RP-1139 revoked is on it. Probes inside a rolled-back transaction prove it bites: a new table's Member id by name and by foreign key, a new column on a table granted by column (`work_item`) and on one granted whole (`work_item_type`), and a new view (seam 1: `apps/api/test/rp-1258-visibility.test.ts`; seam 2: `packages/db/test/rp-1258-visibility-rls.test.ts`) |
