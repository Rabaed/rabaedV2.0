# RP-952 scenarios

Rows of the [scenario matrix](../../visibility.md#scenario-matrix-becomes-the-automated-visibility-test-suite) added under RP-952 (ADR 0028: only the Host Company's Project Admin withdraws a Participant; visibility.md "A Participant's withdrawal"; workflow-engine.md §9), in its setup (Project "Tower": C1 the Host Company, C2 a second Contractor, K1 the Consultant, OR, OW). Seam 1 `apps/api/test/rp-952-visibility.test.ts`, seam 2 `packages/db/test/rp-952-visibility-rls.test.ts`.

| # | Scenario | Who | Expected |
| --- | --- | --- | --- |
| RP-952-1 | C1's Project Admin withdraws C2, which has one item Submitted and with K1, one Draft and one Draft Revision of a closed item | C1 Project Admin; K1 engineer; OR; C1 engineer; C2's Members | The Submitted item is Cancelled by Rabaed: one shared `cancelled` event with no Member and `left_participant_id` C2, outcome `cancelled`, its open Steps `done` at its `closed_at` (RP-955, `app.held_at_close`), and its Documental Record queued. K1, who held it, reads it closed and Cancelled. The Draft and the Draft Revision are Cancelled with no Record and no event anyone else reads; K1, OR and C1 never read either (they never did). The preview the Project Admin read first gave counts only (1 item to be Cancelled, 0 Steps to become Vacancies), never an item, a Document Number or a Member |
| RP-952-2 | Who may withdraw, and who may preview | C1 Project Admin; C1 engineer (not a Project Admin); K1's Authorized Person; C2's Authorized Person; another Project's Project Admin | Only C1's Project Admin previews or withdraws. C1's engineer, K1's and C2's Authorized Persons and another Project's Project Admin get the plain 404, as for an id that does not exist, and nothing changes. The Project Admin withdrawing the Host Company itself is refused 409 `host_company`, and nothing changes. A Participant already withdrawn reads 404 too |
| RP-952-3 | C1's Project Admin withdraws K1 while K1 holds C1's Submitted item at its review Step | C1 engineer and PM; OR; the Owner; C1 Project Admin; C2 | The Step becomes a Participant-level Vacancy (`step_assignment.status` `vacant`, no assignee). C1, OR and the Owner read the item with no holder Company (`with` null) and `vacancy` naming only K1's Project Role ("Waiting for a new Consultant"), never K1's name, in the List, the item detail and the Kanban; the List's "With" filter by K1 no longer finds it; its Step Age keeps counting from when it reached K1. C1's Project Admin reads the Vacancy in the Project's Vacancies list; C1's engineer (not a Project Admin) and C2 get the plain 404 for that list. C2 never sees the item |
| RP-952-4 | The withdrawal's notices | K1's Authorized Person and Project Members; C1, C2, OR and OW Members | K1's Authorized Person and each of K1's Project Members get one in-app notice and one email that name the Host Company (C1) and the Project, never the person who withdrew it. No Member of C1, C2, OR or OW gets a withdrawal notice, in the bell or by email |
| RP-952-5 | After the withdrawal (no undo) | K1's Members; K1's Authorized Person | K1's Members no longer read the Project or any of its items, open or closed (404), except the Documental Records they signed (E2, V8). Everything K1 did stays: C1 still reads K1's moves in the item's history. A second withdrawal of K1 reads 404 |
