# RP-589 scenarios

Rows of the [scenario matrix](../../visibility.md#scenario-matrix-becomes-the-automated-visibility-test-suite) added under RP-589, in its setup (Project "Tower", C1, C2, K1, OR, OW).

| # | Scenario | Who | Expected |
|---|---|---|---|
| RP-589-1 | C1's engineer imports a register (an .xlsx; with RP-644 a .csv whose Package column creates a new Package and adds to an Open one, and C1's saved mapping): previews it, then confirms, creating a Draft for each good row. A C1 colleague, then C2 (another Contractor), K1 and the Owner read imports, rows and results, list the Imports page, and confirm the import | C1 colleague; C2 engineer and Authorized Person; K1 engineer, manager and Authorized Person; Owner PM and Authorized Person | Before confirm, the preview is its importer's only: the colleague reads nothing of it. After, every C1 Member reads the import, its file name, mapping and rows with their reasons; C2, K1 and the Owner read nothing of the import, its rows, its file or its mapping: 404 for the import and its confirm, as for a made-up id, an empty Imports page, no row as the app role, and none of its Drafts. Nobody reads an import's times, a row's Draft id but through `app.register_import_results` (only where they see the Draft), or `work_item.import_id` (seam 1: `apps/api/test/register-import.test.ts`; seam 2: `packages/db/test/register-import-rls.test.ts`). RP-644: no Package exists before confirm; after, the new Package and the Open one added to are read by C1's Members only: C2, K1 and the Owner get the 404 for each and list neither, and `app.sees_package` is false for them. The original register is a 404 to C2, K1 and the Owner, its download names it as uploaded with no time in any header, and C1's saved mapping is listed, renamed or deleted by no other Company (404); an import naming C2's Package by id is refused `package_not_found`, and by name matches none (a new one is created for C1). Admin seam (`apps/admin/test/register-import.test.ts`): the same for a Rabaed Engineer's import as C1's default Member, which offers only the default Member's own Packages and saved mappings, exactly as the customer api does |
| RP-589-2 | C1's PM imports a register assigning rows to a C1 engineer narrowed to Electrical (by email in an "Assign to" column, and by a group rule), and others to a K1 engineer's email, a C1 Member taken off the Project, a deactivated one, an email nobody has and a C1 Member who may not raise the row's Type (RP-640) | C1 PM; C1 engineer narrowed to Electrical; C1 colleague; K1 engineer and manager | The engineer's Electrical rows are good and their Mechanical rows bad (`assignee_outside_visibility`); every assignee who isn't an active Member of C1's Participant on the Project is `assignee_unknown`, naming nobody; one who may not raise the Type is `assignee_cannot_create`. Nobody hears of the import: the confirm writes no outbox row, and no one, an assignee included, gets a notification, email or digest entry. | RP-589-3 | A Rabaed Engineer imports C1's register for C1 in Rabaed Admin (RP-645): picks the Project, C1's Participant and a C1 engineer as the default Member who raises the rows nobody else is assigned, gives a reason, assigns some rows by email and a group rule, previews and confirms. C1's Members then read the Imports page, the import's page and an imported Draft's history; K1 reads the same | The Engineer; another Engineer; C1's default Member, PM and an engineer narrowed to Electrical; K1 engineer and manager | Every row is checked as a Member's import is, the default Member in the importer's place, "Assign to" overriding them per row with the same refusals; a default Member not of C1's Participant or who may not raise Submittals there is refused before anything runs. Each step is an `admin_action` with the reason (V9), never a time. C1's Members read "Rabaed" as who imported, never the Engineer (no name, email or id; `run_by_engineer_id` is not granted), and no time of the import anywhere (the Admin wizard included); the Drafts are the default Member's or each assignee's own, and each Draft's history says, undated, it was imported by Rabaed from that register. The Engineer's preview is theirs alone: the default Member and another Engineer read or confirm nothing of it. K1 reads nothing: 404 for the import and its Drafts, an empty Imports page, no import in a Draft's history. Only Rabaed Admin's role runs the Engineer's functions, and it can't run a Member's. Rabaed Admin's role reads past row-level security, so no check leans on a policy: each says the default Member's Projects, Participant and Visibility itself, and the Engineer's import answers exactly as the default Member's own does through the customer api. With a default Member narrowed to Electrical and Building A, a Mechanical or Building B row is refused with the Member's reason and nothing is created for it; a Paper ref another Participant's item holds neither refuses the row nor shows anything of that item, one C1's own holds is `paper_ref_taken`; "Assign to" naming another Participant's Member, by email or picked by id, is `assignee_unknown`, a C1 Member who doesn't see the row's Trade `assignee_outside_visibility`; the fields and values offered are the default Member's own, no other Participant's Members; once the default Member leaves C1's Participant, the Engineer's preview reads and confirms as none. The import keeps its original register (RP-959): C1's Members download it from the import's page as uploaded, with its own name and no time in any header; C2, K1 and the Owner get the plain 404. Rabaed Admin never touches the file store: its preview hands the file over in the database to `app.hand_over_register_import_original_by_engineer` (Rabaed Admin's role only; the Engineer's own preview that keeps none yet, once), the preview's `admin_action` records `original: handed_over`, and the api stores it at the first download by a Member who reads the import; nobody else's request takes it off the hand-over. Nobody is notified (admin seam: `apps/admin/test/register-import.test.ts`; seam 1: `apps/api/test/register-import.test.ts`; seam 2: `packages/db/test/register-import-rls.test.ts`) |
