# RP-1314 scenarios

Rows of the [scenario matrix](../../visibility.md#scenario-matrix-becomes-the-automated-visibility-test-suite) added under RP-1314: before its own first Submit, a Revision reads its chain's base Document Number with where it stands, "UAT01-MAR-01-0005 Rev 1 · Draft" while it never left Draft and "UAT01-MAR-01-0005 Rev 1 · Internal Review" once it has (owner's decision 2026-11-20, RP-1314 comment 15985; ADR 0030; follows RP-1300). It reads so on every screen that names the item: the item page, the List, the Kanban, the Submittal Panel, a Package's items and its bulk pop-up, the Activity Feed, the Handover dialog and the notifications. The api reads the label through two existing reads, `app.revision_chain` (the base number) and `app.work_item_creation_date` (Draft or Internal Review), which each check `app.sees_work_item`; no new read and no `app.*` change.

Their setup: Project "Tower", C1 the Contractor (its Authorized Person is the Project Admin and a Member of C1's Participant) with an engineer and a PM, K1 the Consultant and C2 a second Contractor, all covering every Trade and Location. Two of C1's MARs are Submitted and closed at Code C by K1; C1's engineer creates Rev 1 of each, keeps one a Draft and sends the other for review, where C1's PM picks it up. Seam 1 `apps/api/test/rp-1314-visibility.test.ts`; seam 2 `packages/db/test/revision-rls.test.ts` (a Revision of the Owner and Owner Representative setup there).

The Vacancies list, the fifth screen, needs no read: before its first Submit a Revision is held only inside its raiser, and a raiser's withdrawal discards its Drafts and cancels what left Draft (`app.withdrawal_cancels`, RP-952), so such a Revision is never a Vacancy. Seam 1 pins it ("the Vacancies list" in the file above): the Host (C1) withdraws C2 while C2 has a Revision in Draft and one in Internal Review, and the list holds neither. Its UI still takes the label, so it would read as the others if that ever changed.
