# Rabaed data model (Project Module, v1 draft)

The logical data model for the platform and the Project Module, in PostgreSQL terms. Names follow [GLOSSARY.md](../GLOSSARY.md). Schedule, Tendering and Financial are out of scope. Each Instance (standard / KSA) runs this same schema independently.

## Conventions

- **IDs** are random UUIDv4 in every table: safe to expose, because they carry no time, and nothing to enumerate. Not UUIDv7, whose creation time would reveal when a Draft was started ([ADR 0015](adr/0015-random-ids-not-uuidv7.md)).
  Being random, an id never orders rows; it only breaks ties. Un-numbered Drafts (and items not yet Submitted) order by Subject, then id; Links by `created_at`, the linked item's Document Number, then id; Documents in upload order (`app.document_times`' `seq`: `confirmed_at`, file name, then id).
- **Bilingual content** entered by customers (names, labels) is stored as `i18n jsonb` (`{"en": "...", "ar": "..."}`), so further languages can be added without schema changes. UI strings are *not* in the database; they are translation keys (Lokalise).
- **Library pattern.** Forms, Workflows, Work Item Types, Positions, Trades and Scopes exist at three levels: `owner_kind ∈ {rabaed, company, project}` + `owner_id`. Using one always **copies** it down a level (`copied_from_id` keeps provenance). Nothing is linked live.
- **Nothing is hard-deleted.** Rows are deactivated, withdrawn, cancelled or closed.
- **Every table carries** `created_at`, `created_by`, `updated_at`. Change history for regulated tables goes to the audit log (§9).
- `→` means foreign key.
- **Finding a function's current body.** The `app.*` functions are redefined across many migrations (the newest by file name wins). `pnpm db:fn <name>` prints the newest definition and the migration and line it is in; `--list` shows every redefinition in order.

## 1. Platform and tenancy

Tenancy is per Project (ADR 0007): every Project-owned table has `project_id` and a row-level-security policy that allows rows only for Projects the current Member participates in. Company-owned tables have `company_id` and a policy limited to the Member's own Company.

**company**
`id`, `legal_name i18n`, `cr_number` (unique), `vat_number` (unique), `status {active, suspended}`, `authorized_person_id → member` (exactly one; nullable only while onboarding), `onboarded_by → rabaed_engineer`, `logo_file_id → stored_file` (nullable: without one, records print the name), `stamp_file_id → stored_file` (nullable, but while it is null no Member of the Company can take a Transition; ADR 0023).
The Authorized Person uploads the logo and the Stamp in the Company profile. Like Signatures they are versioned through `stored_file` (a new upload is a new file), and each record's Record Data keeps the ones in force when the item closed.
As built (RP-617, `20270729000000_company_stamp.sql`): both columns are read like the rest of the row, by the Company's own Members only (`member_reads_own_company`), and the policy `member_reads_own_company_files` on `stored_file` lets them read the files in force, never one replaced, never another Company's. Only the Company's Authorized Person writes them, through `app.set_company_image(company, kind, storage_key, sha256, size, mime, now)` (`kind` is `logo` or `stamp`, PNG or JPEG): it locks the row, adds the `stored_file` row and points the column at it → `set` / `forbidden` (another Member of the Company) / `not_found` (another Company's Member, a made-up id, no acting Member). The api checks the image (its bytes are the type named, at most 1 MB; else `invalid_company_image`, 422, with nothing stored) before storing it under `companies/<company>/<logo|stamp>/<id>.<png|jpg>` (`PUT /v1/companies/:id/logo`, `/stamp`; read with `GET /v1/me/company`); the function refuses (22023, nothing written) a key outside `companies/<company>/<kind>/` or one with `..` (RP-632 review, `20270730000000_review_fixes.sql`), after `not_found` and `forbidden`. `app.member_company_has_stamp(member)` is `take_transition`'s Stamp check (workflow-engine.md §5.1 check 6), and the api's: granted to the app role since `20270730000000_review_fixes.sql`, as an invoker function it reads through row security, so it answers only for the acting Member's own Company (false for anyone else's). In the test database every Company gets a Stamp by default (`packages/db/test-support/test-defaults.ts`; `withoutStamp` opts out).

**member**
`id`, `company_id → company`, `email` (unique per Instance), `full_name i18n`, `phone`, `locale`, `status {invited, active, locked, deactivated}`, `can_create_projects bool` (= Project Creator).
A Member never moves between Companies. Changing employer means a new Member.

**credential**
`member_id` or `engineer_id` (exactly one), `password_hash` (argon2id, PHC string). Authentication is in-house (email + password); Members' MFA factors and lockout counters get their own table and columns later (Rabaed Engineers have them, below). The app role never reads it directly.

**session**
`token_hash` (SHA-256 of the random cookie token), `member_id`, `expires_at`, `revoked_at`. Server-side: signing out revokes the row. Members only: the customer api neither creates nor resolves a session for an Engineer (its `engineer_id` column is left from before ADR 0010).

**invitation**
`member_id`, `token_hash`, `invited_by_engineer_id` or `invited_by_member_id`, `expires_at`, `used_at`. One-time and expiring; accepting it sets the password and activates the Member.

**password_reset** (RP-1058, `20271021000000_password_reset.sql`)
`member_id`, `requested_at`, `token_hash` and `expires_at` (set together when the email is sent), `used_at`, `voided_at`. A forgotten password's emailed link: one-time, valid 30 minutes (`PASSWORD_RESET` in `@rabaed/domain`). No raw token is ever stored, not even in the outbox: `app.request_password_reset` writes the row with no token and an outbox row (kind `password_reset`, the row's id only), and the worker's handler (`@rabaed/db` password-reset.ts) mints the token as it sends the email, storing only its SHA-256 through `app.issue_password_reset`, in the handler's transaction (a failed send rolls it back; the retry mints a fresh one). The request answers `requested` for any email (the api pads every answer to the same time), and `too_many_attempts` past the per-email and per-visitor limits, which count every request alike (`password_reset_attempt`: SHA-256s of the normalised email and of the visitor's address, kept for the window only). Only an active Member of an active Company gets an email; a new request voids their unused links. `app.reset_password` spends the link, voids the Member's other links, sets the password, revokes every session of the Member and records the reset in **member_security_event** (`member_id`, `kind {password_reset}`, `at`; append-only, no token, no password). None of the three tables is granted to the app role or to `rabaed_admin`. Rabaed Engineers are out of scope (ADR 0010). The api: `POST /v1/password-resets` (202, or 429 `too_many_attempts`) and `POST /v1/password-resets/complete` (204 signed in, or 400 `invalid_reset_link` for an unknown, used, voided or expired link).

Identity tables record who created a row through `company.onboarded_by`, `invitation.invited_by_*` and `admin_action` instead of a generic `created_by`.

**member_signature**
`id`, `member_id`, `file_id → stored_file` (unique), `method {drawn, typed, uploaded}`, `active_from`, `active_to` (null while in force; at most one such row per Member, `member_signature_one_active`).
This table is versioned: every signing event points at the exact signature row that was in force, so replacing a signature never changes old records. Signing is blocked while a Member has no active row. Profile → Add Signature draws it (pen styles and colours), types it in a handwriting style, or uploads an image; each is stored as an image. As built (RP-85, `20270727000000_member_signature.sql`): the api checks the image (PNG or JPEG by its first bytes, at most 512 KB), stores it at `members/<member>/signatures/<id>.png|jpg` and calls `app.set_member_signature(storage_key, sha256, size, mime, method, now)`, which ends the row in force and adds the new one with its `stored_file`, under a lock on the Member's row. Read only by its own Member through the app role (row security; the policy `member_reads_own_signature_files` lets them read its `stored_file` rows too); the record job reads others' as the owner. The app role writes neither table. A row changes once, when replaced (`active_to` set), and is never removed (trigger `member_signature_versioned`). `GET /v1/me/signature` gives the Member's own with a short-lived link to the image; `PUT /v1/me/signature` saves a new one (`invalid_signature_image`, 422, for bytes that aren't the image named or are too large). `app.set_member_signature` refuses (22023, nothing written) a key outside `members/<member>/signatures/` or one with `..` (RP-632 review, `20270730000000_review_fixes.sql`). `app.active_signature_id(member)`, `take_transition`'s Signature check, is the api's too: granted to the app role since that migration, as an invoker function it reads through row security, so it gives only the acting Member's own (null for anyone else's). The demo seed gives every demo Member one.

**authorized_person_transfer**
`company_id`, `from_member_id`, `to_member_id`, `by_engineer_id`, `reason`, `at`.

## 2. Projects and participation

**project**
`id` (random UUIDv4, internal and used in URLs), `host_company_id → company` (whose subscription it counts against), `project_number` (per Host Company: 1, 2, 3…, unique `(host_company_id, project_number)`), `code` (short, editable, used in Document Numbers), `name i18n`, `status {active, closed}`, `closed_at`, `show_inspections_in_submittals bool` (default false; RP-652), `planned_completion` (date, nullable; shown as plain text, never counted down or flagged), `creator_member_id`, `record_language {ar, en, bilingual}` (default `bilingual`) and `record_hijri_dates bool` (default false), both set by a Project Admin and applying to records made afterwards (RP-151; below), `working_copy_watermark i18n` (default "Not Final / غير نهائي", never empty; the Project Admin sets it), `origin {direct, tender}`, `tender_ref` (nullable, future).
- `show_inspections_in_submittals` (RP-652): the Project's setting "Show Inspections in Submittals". On, the Project's Module tabs leave out Inspections and the Submittals tab's List, Kanban, Export and Submittals count also read the Inspections Module's Work Items (the work item query's `alsoModules`); a WIR sits in the same Stage group as a submittal of the same Stage key (the Inspections use the Submittals' Stage keys, ADR 0025; RP-674), the group named by the Submittals' Stage. The Module, its Document Numbers, Function Permissions, Workflows, Stages and item URLs are unchanged, and nothing reaches anyone it did not before: the merged read is the same RLS and `app.step_as_seen`. Every Participant reads the column with the Project row; the app role cannot write it. Written only through `app.set_show_inspections_in_submittals(project, show)` → `set` (also when the value is the same) / `not_found` (anyone but the Project's Project Admins, a made-up Project, a null value) / `project_closed`. A change is audited in `setup_event` (kind `project_setting`, type `show_inspections_in_submittals_changed`, payload `from` and `to`; RP-664), only when the value changes: the same value again and a refusal write nothing.
- `record_language` (`bilingual` default, `ar`, `en`) and `record_hijri_dates` (off by default) (RP-151): the language Documental Records are printed in and whether they show the Hijri date beside the Gregorian one. Every Participant reads both with the Project row; the app role cannot write them. Written only through `app.set_project_record_settings(project, language, hijri)` → `set` / `not_found` (anyone but the Project's Project Admins, a made-up Project, a language that is none of the three) / `project_closed`. The record job reads them when it makes the record, so a change applies to records made afterwards. The Working Copy's watermark text is RP-621's: `working_copy_watermark` (bilingual, each 1–60 characters after trimming), written only through `app.set_project_working_copy_watermark(project, text)` → `set` / `not_found` (anyone but the Project's Project Admins, a made-up Project, an empty or too long text) / `project_closed`, read by every Participant with the Project row.

**company_project_counter**
`company_id`, `last_project_number`. Incremented in the same transaction that creates the Project.

**project_admin**
`project_id`, `member_id`, `appointed_by` (member or engineer).

**project_role**
`id`, `owner_kind {rabaed, project}` + `project_id` (null for Rabaed defaults; the library pattern's `owner_id`, named for RLS), `base_role {contractor, consultant, owner, owner_representative}`, `name i18n`, `code`.
A custom role (Subcontractor, PMC…) must name a `base_role`. Permission checks cap at what the base role allows.

**participant**
`id`, `project_id`, `company_id`, `project_role_id`, `ordinal` (1, 2, 3… on the Project, set when it becomes Active; the Company segment of Document Numbers until numbering patterns), `code` (the Participant Code: 2–6 letters or digits, unique in the Project, null until set, when the ordinal stands in; stored in capitals, at least one letter so it never equals an ordinal; fixed once a number uses it or a starting number is set for a counter whose key holds it, recorded in `code_locked_at`, which may be set while the code is null: the position was fixed, so no code can be set (RP-311 review for a starting number; RP-508 for an issued number: a number whose pattern has the Participant segment sets it whether or not the code is null, and `20270120000000_order_fixes_code.sql` backfilled the Participants whose order earlier numbers printed); read with the Participant row, so only its own Company and the Project Admins see it, V15), `code_locked_at`, `status {invited, declined, invitation_withdrawn, active, withdrawn}`, `invited_by_member_id`, `invited_at`, `responded_at`, `withdrawn_at`, `withdrawn_by_member_id`.
Unique `(project_id, company_id)`. A Project Admin's Participant Invitation creates it Invited; the Company's Authorized Person accepts (Active) or declines it (ADR 0009). Invited and Declined rows are seen by nobody but the invited Authorized Person (their own pending invitations) and, as a CR number only, the Project Admins, to whom a Declined one still looks pending. A Project Admin may withdraw an Invited or Declined row (`invitation_withdrawn`, kept for audit and shown to nobody), exactly as they withdraw a lead (scenario 38); inviting the CR number again reopens the same row. Withdrawal of an Active Participant cancels the participant's in-progress Work Items in one transaction (§5).

**onboarding_lead**
`id`, `cr_number`, `project_id`, `project_role_id`, `requested_by_member_id`, `created_at`, `updated_at`, `converted_at`, `participant_id → participant`, `withdrawn_at`, `withdrawn_by_member_id`, `closed_at`. Unique `(project_id, cr_number)`.
A CR number a Project Admin invited that isn't on Rabaed. The Project Admin gets the same answer as for a Company that is, and sees it among their pending invitations by CR number; its details are read only through Rabaed Admin (V9).
When Rabaed onboards a Company with that CR number, each open lead becomes an Invited Participant on its Project, in the offered role, in the onboarding's transaction and `admin_action`. The Participant takes the lead's id and time, so the Project Admin's pending row doesn't change (scenario 31). The lead is then marked converted (`converted_at`, `participant_id`) and kept for audit. Inviting a CR number and onboarding its Company take the same lock on the CR number, so no lead is written after the conversion looked.
A Project Admin may withdraw a lead exactly as they withdraw an invitation to a Company on Rabaed (scenario 38): it leaves their list and Rabaed Admin's, and is never converted. Rabaed Admin may close a lead (`closed_at`, the reason in `admin_action`), which takes it off Rabaed's list only: the Project Admin's row doesn't change, and the lead is still converted if Rabaed onboards the Company after all. Inviting the CR number again reopens a withdrawn or closed lead; if Rabaed onboarded its Company in the meantime, the new invitation takes the withdrawn lead's id, so the row's id never shows that the CR number is now on Rabaed.

**project_member**
`id`, `project_id` (denormalised for RLS; must match the Participant's), `participant_id`, `member_id`, `status {active, removed}`, `removed_at`.
Removal never deletes access to what the Member signed (§10).
`app.member_project_counts()` (RP-413, the Members page): how many active Projects each Member of the caller's own Company is on, counting only active rows of an active Participant of that Company on an active Project. Only the count, never which Projects, and nothing of another Company (V15); no rows for a caller who isn't an active Member.

**position** / **position_permission** / **project_member_position**
- `position`: `id`, `owner_kind/owner_id`, `base_role`, `key` (stable, e.g. `project_manager`), `name i18n`, `sort`, `copied_from_id`. The walking skeleton has Rabaed Defaults only (no `owner_id`, no `copied_from_id` yet).
- `position_permission`: `position_id`, `permission {view, create, submit, review, approve, assign, close, attach}`, `module_key`, `work_item_type_id` (null = whole Module).
- `project_member_position`: `project_id`, `project_member_id`, `position_id` (many-to-many). Set by the Participant's Authorized Person; seen only by that Participant's Company (V14).
- The walking skeleton seeds Rabaed Default Positions only (e.g. Contractor Engineer, Contractor Project Manager) with Module-wide permissions (no `work_item_type_id` yet). The Owner and the Owner Representative each also have a **Project Manager** (`project_manager`: View, Review and Approve in the Submittals), the PM who confirms a Recommended Code in the Owner's review (ADR 0022; RP-593, `20270409000000_owner_review.sql`).

## 3. Visibility, Trades, Locations, Scopes

Trades, Locations and any future dimension share one generic structure, so adding a Visibility Dimension is data, not code.

**visibility_dimension**
`id`, `project_id`, `kind {trade, location, custom}`, `name i18n`, `required_on_work_items bool`.
Every Project gets `trade` (required) and `location` at creation, and the Trade "General" (code `GEN`, RP-627): `app.create_project_dimensions` adds it, as there is no Rabaed default Trade list table yet, and `20270914000000_site_observation_type_and_general_trade.sql` added it to the Projects that existed. A Form's `trade` field may carry `defaultCode` (the code of the Trade a new item starts on; the Site Observation Form names GEN): a starting choice the filler can change.

**dimension_value**
`id`, `dimension_id`, `parent_id` (Location tree: Zone → Building → Floor, three levels; flat for Trades), `depth`, `level_name i18n` (e.g. "Floor"), `code` (2–6 chars, used in numbering), `name i18n`, `copied_from_id` (Rabaed default Trade list), `sort`.

**location_shape**
`dimension_value_id`, `map_file_id → stored_file` (site map or plan image), `polygon jsonb`. Drives the Zone/Plan View.

**location_plan**
`dimension_value_id`, `drawing_id → drawing`. The plan Drawings of a Location, used for Pins.

**scope**
`id`, `project_id`, `trade_value_id → dimension_value` (a Trade of the Project), `parent_id` (null = Scope; set = Sub-scope, in its Scope's Trade), `name i18n`, `status {active, deactivated}`, `sort`. Two levels.
Only Project Admins add, rename and deactivate them; a deactivated one stays on the Work Items that use it. They are not a Visibility Dimension and never grant or restrict access. Built in RP-263; still to come: `code`, Rabaed defaults and the Company lists they are copied from (`owner_kind/owner_id`, `copied_from_id`, "pull updates").

**visibility_grant** / **visibility_grant_value**
- `visibility_grant`: `id`, `project_id`, `subject_kind {participant, project_member}`, `participant_id`, `project_member_id` (set for a Member's grant; `participant_id` is then their Participant), `dimension_id`, `is_all bool`. One per subject and dimension.
- `visibility_grant_value`: `grant_id`, `dimension_value_id`. Granting a Location includes its whole subtree, including Locations added under it later.
- No grant in a dimension covers nothing. A Member's `is_all` means all of their Participant's.

The rule "a Member's grant ⊆ their Participant's grant" is enforced on write: a wider Member grant is rejected, and narrowing a Participant stores each of its Members' grants as the intersection. A Member's effective Visibility (`app.my_visibility`) is also computed as that intersection. A **Visibility Gap** is a query: any dimension value (per role) that no active Participant covers.

## 4. Engines: Forms, Workflows, Work Item Types

**module**: fixed in code: `submittals, inspections, snag_list, site_reports, drawings`.

**stage**
`id`, `project_id`, `module_key`, `key` (stable, e.g. `pending_approval`), `name i18n`, `category {draft, in_progress, closed_positive, closed_negative, cancelled}`, `sort`.
This is the shared set per Module. Workflows reference Stages by `key`, so library Workflows work in any Project.
As built (RP-428, WF-5): `owner_kind {rabaed, project}`. Every Project has its own set per Module, copied from the Rabaed Defaults when it is created (trigger `project_stages`; existing Projects backfilled). An edit of the Rabaed Default Stages (Rabaed Admin, RP-443), a Stage added included, reaches only the Projects created afterwards (decided 2026-10-11, RP-528 review; `20270207000000_default_sets_reach_new_projects.sql` dropped the trigger `stage_rabaed_default_copied` that copied an added one into every Project); a migration that must give existing Projects a new Rabaed Default Stage calls `app.copy_rabaed_stages(project)` for each. A Stage's key moves only by migration, with `app.move_stage_key(module, from, to, name)` (RP-673, the migrator's alone): the Rabaed Default Stage and every Project's copy (a name a Project gave it is kept; where the set already has the new key, the old Stage is dropped), the Steps of every Workflow Version made for a Type of the Module, published ones included, and the items in it. Since ADR 0025 the Inspections Module's set is the Submittals keys (`pending_approval`, `approved`, `revise_resubmit`, `rejected`, moved from `pending_inspection`, `passed`, `failed`). A Rabaed Default Version with a Step in a Stage that an Active Project running that Rabaed Default lacks is refused at publish (`projects_lack_entries`, RP-566; as for outcomes, `outcome` below), and a Project Admin's binding that would put the Project, or one raising Participant, back on a Rabaed Default whose latest Version uses a Stage the Project lacks is refused `default_lacks_entries` (`app.bind_workflow`, `app.unbind_workflow`). Unique `(project_id, module_key, key)`. Every Member of the Project reads them (`member_reads_stages`: they are the Kanban columns everyone sees); the app role writes none. A Project Admin changes them only through `app.rename_stage`, `app.add_stage` (last in the order), `app.reorder_stages` (every key once) and `app.delete_stage`, each under a per-Project-and-Module advisory lock and audited in `setup_event`; outcomes `renamed` / `added` / `reordered` / `removed`, refusals `not_found` (not a Project Admin of it, an unknown Module or key: names nothing), `project_closed`, `invalid_name`, `invalid_stage`, `stage_exists`, `invalid_order`, `stage_in_use`. A Stage keeps its key and its category. A key is snake_case, at most 63 (`app.is_stage_key`, the same cases as `stage.ts` `stageKey`: `stage-key-cases.json`); the Modules are `app.module_keys()` (checked against `module.ts` by seam 2), which the Stage commands and the `module_key` checks of `stage`, `work_item_type` and `position_permission` read. `app.stage_in_use(project, module, key)`: a Step of a Version of one of the Project's own Workflows, or of the Workflow of a Work Item Type of that Module the Project can use, or of a Workflow the Project binds, or ever bound, a Type of that Module to (`workflow_binding_history`, RP-426; so a binding taken away still keeps the Stages of the items raised under it), has that `stage_key`; read from definitions only (which every Participant reads, ADR 0016), never from items. The List, the Kanban, the item page, the Dashboard, Need My Action and the weekly Step Age report read an item's Stage, its name, order and category from its Project's set; whether a Step is a Draft start (`app.is_draft_step`) from the set its Workflow is published against (the Project's for a Project's own Workflow, the Rabaed Defaults' otherwise). A Rabaed Engineer's changes also keep their `admin_action` with a reason.
- `workflow_binding` (RP-426): `id`, `project_id`, `work_item_type_id`, `raising_participant_id` (null: the Type's Workflow on the Project; else an exception for items that Participant raises), `workflow_definition_id`. Read by the Project's Members; an exception only by its Participant's Members and the Project Admins (V15). See workflow-engine.md §1 "Ownership and binding". - `workflow_change_note` (RP-555): `workflow_version_id` (primary key), `change_note text` (1 to 1000 characters), `created_at`. The Change Note written when the Version was published (`app.publish_workflow_with_change_note`; Rabaed Admin's `app.mark_workflow_published_with_change_note`), shown in the Versions history. Append-only; a table of its own because a published Version never changes, and read by the Workflow's authors only (`app.can_author_workflow`), never by every Member who reads the Version (visibility.md RP-555-1).
- `workflow_version`: `id`, `workflow_definition_id`, `version_no`, `status {draft, published}`, `layout jsonb` (React Flow node positions only), `published_at`. **workflow_step**
`id`, `workflow_version_id`, `key`, `name i18n`, `stage_key`, `actor_rule jsonb` (its old `is_signing` dropped by RP-85: every Transition is signed, ADR 0017), `outcome_mode {none, recommend_code, issue_code, inspection_result, confirm_code}` (`confirm_code`: the Owner's review, which issues the Code Recommended to it, ADR 0022, RP-593), `edits_form bool` (nullable), `drafts_visible_to {company, author}` (nullable), `after_send_back {comment, edit_form}` (nullable).
- `edits_form` (RP-514, ADR 0019): whether the raiser's Form is edited at the Step, by the Member holding it, before the first Submit (or at a Step a Send Back leads to). Null is the default, `app.step_edits_form`: a Step of the Draft Step's role held with the Draft Step's Function Permission (form-engine.md §4).
- `drafts_visible_to` (RP-514, ADR 0019): on the Draft Step only; null is `company`. `author`: a Draft is seen by the Member holding it alone (visibility.md V1).
- `after_send_back` (as built, RP-580; ADR 0021): on a raiser's Step a `send_back` leads to, what the raiser may change after a Send Back to it, until the next Submit: `comment` (nothing of the Form) or `edit_form`. Every Version saved or published since RP-580 sets it there (`comment` when left out; `app.publish_workflow_draft` fills it on every publish); null, only on Versions published before, is `edit_form` (form-engine.md §4).
- `actor_rule` says who can hold the Step: base role or project role (`base_role`), or the raiser whatever its role (`{"raiser": true, …}`, RP-622, workflow-engine.md §3.1), required permission (e.g. `approve`), and optional default assignee resolution. The Participant is resolved at runtime from the item's Visibility values; that is how "Electrical goes to Consultant A" works.
- `issue_code` marks the final review Step.

**workflow_transition**
`id`, `workflow_version_id`, `key` (stable within the version, e.g. `send_for_review`), `from_step_id`, `to_step_id`, `label i18n`, `kind {send, submit, return, close, cancel}`, `outcome` (nullable: a closing outcome code of the Work Item Type's set, **outcome**; required when `to_step` is terminal; RP-429), `permission`, `offers_assign_to bool`, `condition jsonb`, `action_form jsonb`, `notifications jsonb`.
- `kind = submit` marks a hand-over between Participants.
- `condition`: routing on Form field values, e.g. `cost_impact > 500000`. As built (RP-430, WF-7): there is no `condition` column; the routing condition is a Restrict rule in `rules`.
- `rules` (RP-430, WF-7): `{ "restrict": [...], "validate": [...] }` as the definition format has them (`transitionRules`, `workflow-definition.ts`); null when the Transition has none. Read at run time by `app.transition_rules` (workflow-engine.md §4, §5.1). Every Member reads it with the Workflow (ADR 0016).
- `action_form`: the pop-up form schema, e.g. pick a Review Code, comments, files.
- `offers_assign_to`: as built (RP-431, WF-8), there is no such column; "Assign to" is an action in `actions`.
- `actions` (`jsonb` array, null for none; RP-431, WF-8): what taking the Transition does besides moving the item, as the definition format has them (`transitionAction`, `workflow-definition.ts`): `{"type": "offer_assign_to"}`, `{"type": "set_field", "field": "<key>", "value": <text, number, yes/no> | {"now": true}}`, `{"type": "copy_field", "from": "<key>", "to": "<key>"}`. Applied at run time by `take_transition` (`app.assignees_offered`, `app.transition_actions`; workflow-engine.md §3.3, §5.1). Every Member reads it with the Workflow (ADR 0016).
- `notifications` (`jsonb` array, null for none; RP-432): whom the Transition notifies besides the next holder or Step Pool, in-app always and email by each Member's own settings: `{"to": "holder"}`, `{"to": "raiser"}`, `{"to": "watchers"}`, `{"to": "position", "position": "<key>"}` (a Position of the acting Participant). Never a person, a group or an email address. Delivered by the watched-item path (`app.transition_notice_members`) for every move the Transition makes, whatever its event's type (`transition`, or `issue_code` for a Code issued); each recipient is checked again at send time.
- `notifications`: who gets what, on which channel.
- `screen_key`, `screen_version_id` (RP-516, ADR 0019): the Screen the Transition shows, by key (null: its own `action_form`), and the Screen Version publishing pinned (`app.workflow_screens`: the owner's Screen with that key, else the Rabaed Default's), whose schema is copied into `action_form` and frozen with the Version (workflow-engine.md §5.7).

- `screen`: a named, reusable Action Form. `id`, `owner_kind {rabaed, project, company}` with `project_id` or `company_id` (the library pattern, like `workflow_definition`, ADR 0016), `key` (snake_case, unique per owner: what a Transition names), `name i18n`, `created_at`, `updated_at`. A Project's Screens are edited by its Project Admins; a Company keeps them in its Library.

- `company_default` (RP-517): `id`, `company_id`, `work_item_type_id`, `kind {form, workflow, screen}`, exactly one of `form_definition_id` / `workflow_definition_id` / `screen_id` (the one of its kind), `created_at`, `updated_at`; unique `(company_id, work_item_type_id, kind)`. **work_item_type**
`id`, `project_id`, `module_key`, `code` (MAR, SAR, DAR…), `name i18n`, `form_definition_id`, `workflow_definition_id`, `outcome_kind {review_code, inspection_result, approval, none}`, `expected_frequency {none, daily, weekly, monthly}`, `allows_subtasks bool`, `copied_from_id`.

The Snag List's Rabaed Default Stages (**stage**): Draft, Open, In Progress, On Hold (RP-90, `in_progress`), Resolved, Closed.

**outcome** (RP-429, WF-6; glossary Outcome)
A Work Item Type's outcome set: `id` (random), `owner_kind {rabaed, project}`, `project_id` (null for a Rabaed Default), `work_item_type_id`, `code` (a letter, then letters, digits or `_`, ≤ 32; never `cancelled`, `pending` or `in_preparation`: `app.is_outcome_code`; its follow-up actions `app.is_outcome_actions`; both run over `outcome-cases.json` with `outcome.ts`), `name i18n`, `closing bool`, `polarity {positive, negative}`, `actions jsonb` (follow-up actions, each kind once: `{kind: create_items, type: <Type code>}`, `{kind: offer_revision}`, `{kind: offer_replacement}`; `app.is_outcome_actions`), `sort`, `created_at`, `updated_at`. Unique `(work_item_type_id, code)` for a Rabaed Default, `(project_id, work_item_type_id, code)` for a Project's. `@rabaed/domain`'s `outcome.ts` is the TypeScript side (`outcomeSchema`, `defaultOutcomeSets`).
- **Rabaed Default sets** (`app.default_outcomes(kind)`, seam-2 `outcome-sets.test.ts` checks it equals `defaultOutcomeSets`): `review_code` A Approved (+), B Approved with Comments (+, create items of `CMT`, WF-11), C Revise and Resubmit (−, offer a Revision), D Rejected (−, offer a replacement, WF-12); `inspection_result` Passed (+), Passed with Comments (+; creating Comments, as Code B does, is to come), Failed (−); `approval` Approved (+), Rejected (−); `none` Closed (+). All closing.
- **Seeding**: a new Type gets the set of its `outcome_kind`, owned as the Type is (trigger `work_item_type_outcomes`); a new Rabaed Default Type's set is also copied into every Project then, so a Project can run the Type at once. A new Project copies them all (trigger `project_outcomes`), so every Project runs its own copy of each Rabaed Default Type's set, as it runs its own Stages. Backfilled for existing Types and Projects. An edit of a Rabaed Default set (Rabaed Admin, RP-443: an outcome added, a name or follow-up action changed, the order) reaches only the Projects created afterwards; no existing Project's copy changes (decided 2026-10-11, RP-528 review; the trigger `outcome_rabaed_default_copied` that copied an added outcome into every Project is dropped). So a Rabaed Default Version whose Transition sets an outcome that an Active Project running that Rabaed Default has no closing outcome of in its copy is refused at publish, `projects_lack_entries` with how many Projects and which outcomes, never which Projects, and logged in `admin_action` as `refuse_workflow_publish` (RP-566, `projectsLackingOutcomesAndStages`; workflow-engine.md "Rabaed Admin -> Workflows"); its Project Admin adds the outcome first. Likewise a Project Admin's binding that would put the Project, or one raising Participant, back on such a Rabaed Default is refused `default_lacks_entries`, naming the Project's own missing outcomes and Stages (`app.binding_lacks_entries`, to its Project Admins only).
- **Visibility**: read like the Type (`member_reads_outcomes`, the rule of `member_reads_work_item_types`): a Rabaed Default set by every Member, a Project's copy by its Project Members only. The app role writes none.
- **Commands** (Project Admin, the Project's copy only; a Rabaed Default set changes only in Rabaed Admin, as Seeding says, reaching only the Projects created afterwards): `app.add_outcome(project, type code, code, name, closing, polarity, actions)` (last in the order), `app.change_outcome(project, type code, code, name, actions, new code, closing, polarity)` (the last three null: kept; decided 2026-10-09: code, closing and polarity change only while the outcome is unused, `app.outcome_in_use`: no closing Transition of a published Version the Project's items can run names it, i.e. the Project's own Workflows, the Rabaed Defaults for the Type, the Type's default Workflow and every Workflow the Project ever bound the Type to; read from definitions only, never from items, since whether a hidden item closed with it would leak to a Project Admin not on its Documental Record, and an item's outcome only ever comes from such a Transition, so an unused outcome closed no item; refused `outcome_in_use`, the api 409 with an English and Arabic message; a change of them is audited with `code`, `closing` and `polarity` in the event's `from` and `to`), `app.reorder_outcomes(project, type code, codes)` (every code once). The Type is the Project's own of that code, else the Rabaed Default (`app.project_type_id`). Each under a per-Project-and-Type advisory lock and audited in `setup_event`; outcomes `added` / `changed` / `reordered`, refusals `not_found` (not a Project Admin of it, a Type the Project doesn't use, a code the set lacks: names nothing), `project_closed`, `invalid_outcome`, `outcome_exists`, `invalid_order`, `outcome_in_use`. Nothing deletes an outcome.
- **Reads of follow-up actions**: `app.outcome_offers(project, type, code, action kind)` (invoker), `app.work_item_outcome_actions(item)` (the actions of the outcome a closed item ended with, for a caller who sees it; `[]` otherwise), `app.can_create_revision` (an outcome offering a Revision, Code C).
- The api: `GET|POST /v1/projects/:projectId/work-item-types/:type/outcomes` (`TypeOutcomes`, with `canEdit`), `PUT …/outcomes/order`, `PATCH …/outcomes/:code`; `invalid_outcome` 422, `outcome_exists` 409, `invalid_order` 422, anyone else the plain 404.

Written only by `app.sync_work_item_checklists(item, now)`, which the API calls in the same transaction as every create and Save draft of an item whose Form has such a field: for the Member who may save the item's answers now (`app.can_save_answers`, else `not_editable`), a copy follows its answer (kept while it names the same Version, replaced by a new pick, deleted with the answer); after the item's first Submit replacing or deleting a copy is `checklist_fixed`, while a missing one is filled in (no change of the pick); a new copy takes only the latest Version of an active template of the Project for the item's Trade, read under a share lock on the template (RP-651 review, `20270716000000_checklist_templates_review_fixes.sql`), or, on a Revision, the Version the item it revises holds; anything else is `template_not_found`. The api also calls it when a Revision is created and before a forward Transition by a Member who may save. The item read carries it as `checklistCopies`.

**reply_checklist** (a reply Screen's checklist answers until its Transition; as built, RP-86; form-engine.md §3.3, workflow-engine.md §5.7)
`id`, `project_id`, `work_item_id`, `field_key` (the Screen's `copied_checklist` field), `answers jsonb` (by check item, as the api checked them; an item that raises a Snag keeps `"snag": false` when its "Raise a Snag" tick was taken off, RP-577), `participant_id` (the holding Participant that fills it), `updated_by_member_id` and `updated_at` (audit only, not granted), `reply_event_id` (the Transition's event that took it; deferred foreign key). One row waiting per item and field (`reply_checklist_waiting_key`, where `reply_event_id` is null); each Transition taken keeps its own. The app role reads `work_item_id`, `field_key` and `answers` of the rows waiting, and only as a Member of the Participant holding the item (`app.holds_work_item`, V19); once taken, the Transition's event shares the answers. Written only by `app.save_reply_checklist` (and the triggers that take or discard it, workflow-engine.md §5.7). `document.reply` rows may now name an `item_key` (a check item's photo; `document_reply_has_field`).

**outbox**
`id`, `kind` (`notification`, `email`, `digest`, `step_age_report`, `documental_record` (RP-620, §6), `record_ready` and `documental_record_reproduce` (RP-155, §6), `working_copy` (RP-621: a Working Copy a Member asked for, payload `{working_copy_id}`, §6) as built; package_recompute… to come), `project_id` (null for a row that spans Projects, such as a Member's daily digest), `payload jsonb` (ids only, never customer text), `created_at`, `available_at` (next due), `processed_at`, `last_failed_at` (when an attempt last failed, set with `last_error` by `app.outbox_failed`; RP-670), `attempts` (failed attempts: counted when a row is taken, in its own committed step, and given back when the attempt succeeds, so a worker that dies in the handler still spends one; RP-958. While a handler runs, or after its worker died, it includes the attempt in flight, as the Job Monitor shows it, RP-670), `last_error`, `dead_at` (dead-lettered after the last attempt). Written in the same transaction as the command that caused it, or by a scheduled job; the worker takes one due row at a time (`FOR UPDATE SKIP LOCKED`), pushing its `available_at` back by the attempt's backoff, then runs it in a second transaction holding the row's lock (workflow-engine.md §5).

**scheduled_job_run** (RP-358)
`job` (primary key, e.g. `daily_digest`), `run_at` (the latest run time it ran for), `ran_at`. The worker's only: no grant to the app role. The worker works out a job's due run time from its schedule (`dueRun` in `@rabaed/domain`) and claims it with `app.claim_scheduled_run(job, run_at)` in the transaction the job runs in, so a run time runs once however many workers poll, and a failed job runs again.

**numbering_pattern**
`id`, `project_id`, `work_item_type_id` (null = Project default), `segments jsonb` (≤ 6 of: project code, type code, trade, participant code, location level, custom literal), `separator` (`-` or `/`), `seq_digits (3–7)`, `seq_scope jsonb` (the positions, from 0, of the segments the counter counts separately for), `shared_counter_accepted_at` (required when `seq_scope` leaves out the participant code; the setter is the one who accepts), `set_by_member_id` or `admin_action_id`, `effective_from`, `follows_project` (a Work Item Type's row saying the Type uses the Project pattern again from then; its pattern columns are null). Project Members read their Project's patterns; a Project Admin saves one through `app.set_numbering_pattern`, in effect from then. Rows are never changed or deleted: each is a version, read with who saved it through `app.numbering_pattern_versions` (RP-412 rebuild; the saver's Company per V15, the person within the reader's own Company only, V14). The Numbering page calls a Type's pattern its **Custom pattern**.
A pattern change creates a new row, and old numbers stay as issued. No row means the Rabaed Default: project code, type code, participant code, sequence of 4, counted by all three (settled 2026-10-05). The number is built by `app.document_numbering`, the database's copy of `documentNumbering` in `@rabaed/domain` (the web's live example); the two must agree.

**numbering_counter**
`project_id`, `counter_key` (resolved prefix), `last_value`, `starting_value` (set when created ahead; it has issued nothing while `last_value = starting_value - 1`).
Incremented with `INSERT … ON CONFLICT DO UPDATE … RETURNING` (the first number creates the row) in the same transaction as the first Send or Submit, so there are no gaps and no reuse.
The key is the values of the pattern's counted segments joined by `-`, whatever the separator; under the Rabaed Default `<project code>-<type code>-<Participant Code or ordinal>`, so each Participant counts on its own (e.g. `TWR-MAR-01-0001`). A new pattern counting by the same values continues the same counter. A counter can be created ahead with a starting `last_value` by a Project Admin or Rabaed Engineer, only while it has issued nothing; doing so fixes the Participant Code its key holds. A value whose number the Project already used (another counter built it, after a pattern change) is skipped at issue, never issued (RP-311 review). Only Project Admins and Rabaed Engineers read counters.
A number names the Trade and Location it was issued with, so those never change afterwards (RP-581, ADR 0021): `app.number_fixed_fields(work_item_id)` reads the pattern in effect at the item's `numbered_at` and returns `trade` and/or `location` when its segments hold a Trade or a Location level; `app.check_work_item_built_ins` then refuses a changed value as `number_part_fixed`.

**command_idempotency**
`member_id`, `key`, `project_id`, `work_item_id`, `command`, `created_at`. Primary key `(member_id, key)`. Written in the same transaction as the command; the same key again applies nothing. No read policy: the app role reads it only through `app.command_keys_used(keys)` (RP-646, `20270817000000_bulk_transitions.sql`), how many of `keys` the caller has already applied a command under, never which item or command.

- `app.sees_package(package)`: its owner (`app.owns_package`), or, once it is no longer `open`, a Member who sees (`app.sees_work_item`) at least one of its items (RP-641).

- `app.package_latest_items(package)` → (`work_item_id`, `counted`) (RP-616 review fix 18, `20270819010000_package_latest_revisions.sql`; spec story 30): `app.latest_revisions` of the items the caller sees (`app.package_items`). `app.latest_revisions(items)` (RP-976, not for the app role) is the rule, once, for this and the Package's Done: of the given items, not discarded, the latest Revision of each chain (`root_id`, highest `revision_no`), a cancelled one left out so a cancelled R1 gives the Code C back; a chain of only cancelled ones gives its latest, `counted` false. Per viewer, so a Revision they don't see never counts for them. The Package page lists these.
- `app.package_summary(package)` → (`total`, `open`, `codes`) (RP-641; story 30 since review fix 18): of the `counted` ones of `app.package_latest_items` (a Code C and its open R1: open 1, total 1), how many, how many still open, and the closed ones by outcome (the Review Code) as `{"A": 2, "C": 1}`; no row when they don't see the Package. The board's and the Package page's counts.
- `app.package_owner_name(package)` (RP-641): the owning Participant's Company name (V14), for every Member who sees the Package; else null.
- `app.work_item_package(item)`: the item's Package (`package_id`, `seq`, `name`) where the caller sees both the item and the Package; else no row. The work item query gives it on each row (`package`), and the item's page too, each with its owning Company's name from `app.package_owner_name` (`companyName`, V14; RP-974: the chip shows it next to the number, since two Participants' Packages can both be PKG-001).
- `app.package_comments(package)` → (`work_item_id`, `raised_from_id`) (RP-647, `20270818000000_package_comments.sql`): the Comments (Type `CMT`, raised by Code B, RP-434) whose `raised_from` link names one of the items the caller sees (`app.package_items`), each one the caller sees (`app.sees_work_item`, as `app.work_item_comment_counts` counts them), never a discarded one; nothing when they don't see the Package. A Comment has no `package_id`: it is never one of the Package's items, nor in its counts or status.

The work item query's `packageId` filter (RP-647) keeps the rows in `app.package_items(package)`: a Package the caller doesn't see filters to nothing, the same answer as a made-up id. `GET /v1/packages/:id/comments` gives `PackageComments` (`forInformation: true`, each Comment as the Snag List's row gives it, with the submittal it was raised from), or the plain 404.

The api's board (`GET /v1/projects/:id/packages`) and Package page (`GET /v1/packages/:id`) give each Package as `PackageSummary` (with `counts`), the page its items as `PackageDetailItem`: each item's own row of the work item query (`workItemRowsById`), so "With" follows V14 as in the List, the latest Revision of each chain the viewer sees (`app.package_latest_items`, story 30), with `bulkTransitions`, `toSubmit` (still to Submit by Submit Package's own rule, for the owner only) and `notReady` (RP-974: why it stops Submit Package before any attempt, `pick_up_first` or `cannot_submit` as the 409 names them, null when nothing of it does and always for a viewer outside the owning Participant); the page also gets `owned`, `othersNotReady` (an item still to Submit the owner doesn't see stops it, `app.package_hides_unsubmitted`, never which; false for any other viewer) and the table's `filters` (the Types' outcomes on the Project, its Trades and Locations, `outcomeAndDimensionChoices`), so the web reads the items once and works out no rule of its own (review fixes 9, 10). A viewer outside the owning Participant is offered no action. Each `PackageSummary` also carries its `trades` (RP-953): the Trades of the items its page lists to the viewer (`app.package_latest_items`), each as the viewer may know it (`work_item_dimension_value_seen`, V19), in the Project's order of Trades. The Packages view's search (the PKG number, the name in either language) and its Trade and owning Company filters work on those Packages in the web (`filterPackages`, `packageFilterChoices` in `@rabaed/domain`; each Trade carries its `sort`, so the Filter panel lists them in the Project's order too, product owner 2026-10-20), kept in the URL (`q`, `trade`, `company` beside `view=packages`), so every choice comes from what the board API gave the viewer.

Writes (security definer, each re-checking the caller; a Package the caller doesn't own is `not_found`, whether or not they see it, a Project not active `project_closed`):
- `app.create_package(project, name, now)` → (`outcome`, `package_id`, `seq`): any Member of a Participant on the Project, for their Participant; `created`, `not_found`, `project_closed`, `invalid_name`. The next `seq` under an advisory lock per Project and Participant.
- `app.rename_package(package, name, now)`: `renamed`, `not_found`, `project_closed`, `invalid_name`.
- `app.add_package_item(package, item, now)`: only a submittal (a Type of the Submittals Module) the owning Participant raised, that the caller sees and that isn't discarded, else `item_not_offered` (one answer whatever the reason); `in_another_package` when it is in another; `not_editable` for a Draft (no Document Number) the caller may not edit (`app.can_save_answers`); `added`, also when it already is in this one.
- `app.remove_package_item(package, item, now)`: while `open`; `removed`, `package_not_open`, `item_not_in_package` (not in it, or not seen).
- `app.discard_package(package, now)` (the Package's Delete): while `open`; its items keep everything but their Package; `discarded`, `package_not_open`.
- Helpers, not for the app role: `app.package_for_write(package)` (the row locked, if the caller owns it: `app.owns_package` since RP-641), `app.write_package_event` and `app.recompute_package_status(package)`.

**Submit Package** (RP-638) is a command of the api (`submitPackage` in `apps/api/src/packages/packages.ts`), not of the database: for each item of the Package the caller sees still to Submit (`app.package_items_to_submit`), their Submit Transition (kind `submit`, from `app.work_item_actions`) taken through `takeTransitionIn`, the single Submit's path and its `app.take_transition`, all in one transaction; any refusal rolls back all of them. Each item's key is derived from the request's key and the item. The database gives it:
- `app.begin_package_submit(package, key)` → (`outcome`, `work_item_ids`): the Package locked; `ready`, `replayed` with the items the caller's same key Submitted before, `not_found`, `project_closed`.
- `app.record_package_submit(package, items, key, now)`: the `submitted` event of the trail, once each item is in the Package and Submitted; `recorded`, `not_found`, `item_not_submitted`.
- `app.package_unsubmitted(package)` (RP-976, not for the app role): the rule "still to Submit", once: every item in the Package without `submitted_at`, not closed, not discarded. `app.package_items_to_submit(package)`: those the caller sees (`app.package_items`), what the api's Submit Package and its readiness read.
- `app.package_hides_unsubmitted(package)`: whether an item still to Submit (`app.package_unsubmitted`) is one the caller doesn't see; such an item stops their Submit Package, which says so without naming it. False for anyone but the owner (`app.owns_package`, RP-641), so a viewer of another Company never learns an item is still to Submit.

`POST /v1/packages/:id/submit` answers 200 with the items Submitted (`submitted`), or refuses with the api's own codes besides `not_found`, `project_closed` and `not_confirmed`:
- `package_not_ready` (409): nothing was Submitted; `notReady` lists each item the caller sees that stops it, with why (`PackageNotReadyReason`: `pick_up_first`, `cannot_submit`, `form_incomplete`, `invalid_action_form`, `validation_failed`, `no_signature`, `no_stamp`, `refused`), and `othersNotReady` says whether an item they don't see stops it too (`app.package_hides_unsubmitted`), never which.
- `nothing_to_submit` (409): every item the caller sees is Submitted already (or closed), and none they don't see is still to Submit.

**Bulk Transitions** (RP-646) are a command of the api (`takeBulkTransition` in `apps/api/src/work-items/bulk-transitions.ts`, `POST /v1/work-items/bulk-transitions`), not tied to Packages and not of the database: a list of item ids, one Transition key, one set of Action Form answers, one Internal Note and one optional "Assign to" pick. Accepted only when every item is one the caller sees (else the plain 404), waits on them (`app.need_my_action` = `waiting`), and offers them that Transition (`app.work_item_actions`) with the same Action Form: its `workflow_transition.screen_version_id`, or for an inline one its `action_form`. Then each item's Transition is taken through `takeTransitionIn` and `app.take_transition`, with a key derived from the request's and the item, all in one transaction; the first refusal rolls back all of them, and the 409 `bulk_refused` names that item (as the caller reads it) and why (`BulkStop`). The same request again replays (every derived key used, `app.command_keys_used`); a key used for other items is `idempotency_key_reused`. There is no signing check of its own: since ADR 0017 every Transition is signed and no Step or Transition is marked as signing (`workflow_step.is_signing` is read by nothing; RP-85 drops it). The Package page gives each item's `bulkTransitions` (`bulkOffers`): the Transitions the viewer may take on it now with their Action Form (`form`), none when it doesn't wait on them; a selection shares one when every item offers the same key and `form`.

**package_event** (RP-636)
`id`, `project_id`, `package_id`, `type {created, renamed, item_added, item_removed, submitted, discarded}`, `work_item_id` (set exactly for `item_added` and `item_removed`), `actor_member_id`, `actor_participant_id` (the owning Participant), `payload` (`created`: the name; `renamed`: `from` and `to`; `submitted`: `work_item_ids` and the request's `idempotency_key`, RP-638), `created_at`. The Package's own trail, internal to the owning Participant. Append-only (trigger), and not readable through the app role until a reader is built.

Status is recomputed on Submit, when a submittal, Revision or replacement joins it, and on every member item's closure, cancel or discard, in the same transaction (as built, RP-642). The Package is Done when every *latest revision* in it closed at A, B or D; cancelled and discarded items are left out.

**Lock order** (RP-616 review fix 5, `20270819000000_lock_order.sql`). A single Transition locks its item (`app.take_transition`'s update), then its Package (the status trigger, `app.recompute_package_status`, `for update`). A command over several items, Submit Package and a bulk Transition, locks all its items first, in order of id (`app.lock_work_items(ids)`: the ones the caller sees, `for update`, until the transaction ends), then the Package, so it and a single Transition never wait on each other the other way round. Both go through `apps/api/src/work-items/several-transitions.ts` (`lockWorkItems`, then `takeEach`). Submit Package locks the items still to Submit before `app.begin_package_submit` locks the Package; an item added between that read and the Package's lock is locked when it is taken. An Open Package's own writes take the same order (RP-973, `20271003000000_package_write_lock_order.sql`): `app.add_package_item` and `app.remove_package_item` lock their item through `app.lock_work_items` (an item the Member doesn't see is not locked, and they return before writing it), and `app.discard_package`, for an owner of the Package only, locks every item in it by id, the ones the Member doesn't see too, since it takes them all out (`20271004000000_discard_package_locks_unseen_items.sql`); then `app.package_for_write` locks the Package. Before, they locked the Package first, so removing an item or deleting the Package while that item was being Submitted could deadlock. An item added between the delete's read and its Package lock is still locked after the Package, so only a Submit of that same item in that instant could still wait on it the other way round. Seam 1 checks the order of each command (`test/support/lock-order.ts`).

## 6. Documents, signing, Documental Records

**stored_file**
`id`, `storage_key` (object storage, unique), `sha256` (`bytea`, the stored bytes' 32-byte SHA-256), `size` (bytes), `mime`, `uploaded_by_member_id → member` (null when Rabaed made the file, such as the record job's PDF), `created_at`.
One row per file Rabaed keeps outside Documents: a Member's Signature image (RP-85), a Company's logo and Stamp, a Documental Record's PDF and Record Data. A new upload is a new row, so whatever pointed at the old one keeps it. As built (RP-85, `20270708000000_stored_file.sql`): immutable, since triggers refuse update, delete and truncate for every role. Row security is on with no policy of its own: each table that points at a file adds the policy that lets its readers read that file's row (`member_signature`: the Member's own Signature files; `company`, RP-617: its own Members read its logo and Stamp in force). The app role is granted `id`, `storage_key`, `size`, `mime` and `created_at` only, never `sha256` or `uploaded_by_member_id`, and writes nothing; rows are written by `app.*` functions and the record job. `rabaed_admin` may not insert, update, delete or truncate.

**document**
`id`, `project_id`, `work_item_id`, `file_name`, `size_bytes`, `content_type`, `storage_key` (`projects/<project>/work-items/<item>/documents/<id>`, ADR 0007), `uploaded_by_member_id`, `uploaded_by_participant_id`, `created_at`, `confirmed_at`, `removed_at`, `removed_by_member_id`, `frozen_at`, `field_key` (nullable), `item_key` (nullable, only with a `field_key`), `taken_at`, `taken_latitude`, `taken_longitude` (nullable).
A file attached to a Work Item: in the Attachments System Field (RP-269), or, with a `field_key`, in one of the Form's `attachments` or `photos` fields (RP-281, RP-284), whose content types and maximum the upload functions check, or, with a `field_key` and an `item_key`, as the photo evidence of one item of a `checklist` field (RP-285: images only, at most 10 an item, only for an item that takes photos). An image keeps when and where it was taken (`taken_*`), which the api reads from the stored file's EXIF when it confirms the upload, never from the browser; null when the file records none. Read under the item's own RLS; written only through `app.*` functions. Upload is three steps: a pending row and a signed PUT URL for exactly the declared size and type, the browser's upload, then a confirm once the api finds the file in storage (`confirmed_at`). Until confirmed, and once removed, nobody sees the row. The raiser's Participant, with the Attach permission, adds and removes Documents while the item is in Draft; removal marks the row and keeps the file.
Frozen at the first Submit (ADR 0020; RP-515: the trigger `work_item_freezes_documents_at_submit` when the item, once Submitted, crosses to another Participant, or closes, a Cancel without a Submit included (kept, product owner 2026-10-11); before, when it left Draft). After that the row can't change, even for its owner, and a change needs a Revision. Until then the holder of a raiser's Step that edits the Form adds and removes them (the Contractor Engineer Step after a Return too); one added after a Send Back is frozen at the next Submit.
`arrival` (RP-309): the item's `arrivals` when the row was added, set by a trigger. A Document added while the item is held (the raiser's Draft after a Send Back) is seen only by the holding Participant until the item leaves it; everyone else reads the Documents it had when it arrived (`app.item_row_seen`, in the RLS policy, so lists and downloads agree). A Document others have seen is frozen, so never removed.
A Revision's Documents are copied as new rows with their own storage keys; **document_copy** (`document_id`, `copied_from_id`) records each one's source so the api copies the file, and is never granted to the app role (RP-316). A copy keeps its source's `created_at` and `confirmed_at` (its `uploadedAt`), never the Revision's start, so it carries no Draft-started time (RP-393, scenario 75).
`reply` and `reply_event_id` (RP-623, ADR 0024): `reply` marks a file of a reply Screen's `photos` or `attachments` field (its key in `field_key`, never one of the item's Form, no `item_key`), added by the Participant holding the item; `reply_event_id` names the Transition event that took it (it freezes then; a deferred foreign key to `work_item_event`), null while it waits. One waiting when the item leaves that Participant any other way is removed. Selectable by the app role; workflow-engine.md §5.7 "Documents in a reply".

`annotated_from_id` (RP-656): set on an **annotated copy**, the image drawn on a photo in the shared photo tool (`packages/ui` `PhotoTool`), naming the original photo it was drawn on. The original is never written again: its row and its stored bytes stay as they were, and it stays the evidence. The copy is a Document of its own (its own storage key) on the same item (a foreign key on `(annotated_from_id, work_item_id)`), with the original's `field_key` and `item_key`, and its time and place (the drawn image has no EXIF; a trigger copies them on confirm). It is read under the same RLS, so exactly where the original is (visibility.md RP-656-1). Started by `app.start_annotated_copy_upload(item, original, file name, size, content type, now)` → `started` / `not_found` (item or original unseen, or the original itself a copy) / `project_closed` / `forbidden` / `not_editable` / `document_frozen` (a frozen original takes no new copy) / `content_type_not_allowed` (the original isn't a photo, or the copy isn't JPEG, PNG or WebP) / `field_not_found` (a reply photo whose field takes nothing at the item's current Step, RP-981); the api's `POST /v1/work-items/:id/documents` with `annotatedFromId` calls it, and the usual confirm finishes it. One live copy an original (a partial unique index): confirming a new one removes the previous one, and removing the original removes its copy (triggers). Copies count toward no field's maximum or checklist item's 10 photos, and a field's file types apply to the original only (`app.field_document_refusal`); nor do they count in a field's files for leaving Draft. A reply Screen's photo (RP-981) is annotated by the Members who may add to its field now (`app.reply_documents_refusal` and `app.reply_field_refusal`, not `app.can_change_documents`), and its copy is a reply Document (`reply = true`): the Transition that takes the original takes it too, and leaving the Participant any other way removes it (visibility.md RP-981-1). Confirming such a copy is `not_editable` once a Transition took its original. A trigger (`document_annotated_copy_where_original_is`) refuses a copy whose `reply`, `field_key` or `item_key` differ from its original's. A Revision's copy of a copy is linked to its copy of the original (a trigger on `document_copy`). `DocumentSummary.annotatedFromId` carries it; `withAnnotatedCopies` (domain) pairs each original with its copy, and `isAnnotatedCopy` keeps copies out of the views that list files.
`created_at` and `confirmed_at` are not granted to the app role: a Document added during the Draft keeps its real time, for audit. `app.document_times` gives each visible Document its upload time (the api's `uploadedAt`), no earlier than the Creation Date of the item it was first uploaded on once that item is numbered, so a copy follows the original's Creation Date and a Revision's own Documents its own; while that item is a Draft, real times. It also gives the order they were uploaded in (`seq`) (RP-399, scenarios 61 and 75).
`stored_file` (with its `sha256`) comes with the Files Module and the Documental Record; until then the file's details live on the Document. A Document has `file_sha256` (as built, RP-618): its bytes' fingerprint, which the api works out from the stored file, streamed, when it confirms the upload, and passes to `app.confirm_document_upload` (a confirmation without one is refused, `upload_mismatch`). A Revision's or a replacement's copy takes its source's as its `document_copy` row is written (a trigger), a Duplicate's in `app.copy_duplicate_documents`. It is not granted to the app role, like the content hash it joins (workflow-engine.md §7). Null only on Documents confirmed before RP-618 (dev and UAT data). The Documental Record prints it beside each file of its appendix, read by the worker through `app.documental_record_facts` (RP-147).

**documental_record**
`id`, `work_item_id` (unique: one record per item), `pdf_file_id → stored_file`, `record_data_file_id → stored_file` (the Record Data XML, also attached inside the PDF), `layout_version`, `language`, `outcome`, `pdf_sha256`, `sealed_at`, `verification_token_hash` (the QR's long link), `verification_code` (the short printed code, unique with the Document Number), `status {preparing, published, failed_checks}`.
Produced on every closure from its Record Data (ADR 0023). The PDF names everyone who took a Transition on the item's path to its outcome, whichever Company (name, Position, Company, date, Signature, Stamp), but no Returns, Internal Notes, Recommended Codes, Chat or in-progress answers (visibility.md V7, ADR 0017). It is PDF/A-3, sealed with PAdES B-LT and a timestamp. Its location, name and URL never change.
As built (RP-620, `20270709000000_documental_record.sql`): also `project_id` and `created_at`; `verification_token_hash` and `verification_code` are each unique on their own (the code is `XXXX-XXXX` in Crockford's base 32); `status` is written `preparing` and moved by the checks (RP-155, below): the trigger lets it move only from `preparing`, to `published` or `failed_checks`; a record whose checks failed is published again only by a Re-produce. Both files are `stored_file` rows with no uploader (Rabaed made them), at `projects/<project>/work-items/<item>/documental-record/record.pdf` and `…/record-data.xml`. The row is written once (trigger `documental_record_written_once`): the only change allowed is `status` moving forward, `preparing` to `published` or `failed_checks` and `failed_checks` to `published`, for RP-155's checks; Re-produce gets its own function (RP-155, below).
**RP-151** (`20270720000000_record_page_one.sql`): `app.documental_record_facts` is rebuilt to also give the worker what page 1 and the Form print (the Submission Date, the Revision's source and its outcome, the Companies on the item with their Project Roles, the Project's Trades with the item's marked, Location and Scopes, the Type's closing outcomes, the issued Code's Remarks from its shared `issue_code` event, the number of Review Comments, the Form Version's sections with `app.record_form_answers`, the Option Lists, Approved Suppliers and Company names those answers use, the Documents, the Project's record settings; each Transition also gives its Company's Project Role, its kind, the Step's outcome mode and, for a Code's own shared event, its Remarks: the reply printed is the one on the path's Code that is the outcome, so a Code the Owner sent back, and any Cancel's, never print). Still never read: Returns' reasons, Internal Notes, Recommended Codes, Chat, in-progress answers, the Draft-started time. `app.shared_answers_of(item)` is the body `app.work_item_shared_answers` had, without a calling Member (not granted to the app role): `app.work_item_shared_answers` (redefined by this migration, same result) checks `app.sees_work_item` and calls it, and the facts function calls it once. `pdf_template` and `pdf_template_version` were never built.

## 10. Access rules that cut across tables

1. **Seeing a Work Item** requires all three:
   - an active `project_member`,
   - a `work_item_access` row for the Member's Participant,
   - the Member's Visibility covering every dimension value of the item.

   If the item is still in the raising Participant's internal Steps, only that Participant qualifies.
2. **Signatory Access** is a query, not a copy: every `work_item_event` with `signature_id` whose `actor_member_id` is you entitles you to that item's Documental Records and the Project's name. This holds even when you're removed or the Project is Closed. The same applies to your Company's Authorized Person.
3. **Closed Project**: every write path checks `project.status = active`.
4. **Withdrawn Participant**:
   - in one transaction, every open item with `raised_by_participant_id` = it gets a `cancelled` event, `outcome = cancelled` and a Documental Record;
   - open `step_assignment` rows for it are closed.
5. **Rabaed Engineers** go through `admin_action` only. They have no path to insert `issue_code`, `recommend_code` or `transition` events.
6. **Form answers** (ADR 0012): the app role can't read `work_item.data`. It reads the answers through `app.work_item_answers`, which re-checks that the caller sees the item and strips every reference they may not see: a `member` answer naming anyone outside their Company, and a `participant` answer naming a Participant other than their own, the Host Company's or one on the item. `app.answers_sha256` hashes the full, unstripped answers, and answers only while they are open (only the raiser sees the item then); the hash chain hashes `title` and `data` as before. A new field type that stores an id adds its strip rule there, with a seam-2 test.
7. **Reading items at scale** (RP-1050, `20271019000000_reads_at_scale.sql`). Rule 1 is one function, `app.sees_work_item(item)`, and every read asks it once per item it reads, never once per item in the database:
   - `work_item`'s policy is `project_id in (select app.current_project_ids()) and app.sees_work_item(id)`; the prefix is part of the rule and lets a read of many rows skip other Projects' items cheaply.
   - A table read through the item's own (`work_item_event`, `step_assignment`, `work_item_access`, `notification`, `document`, `work_item_link`, `work_item_checklist`) asks `app.sees_work_item(<its item column>)` for each row read. `work_item_dimension_value` and `work_item_scope`, which also read the item's values as it arrived (V19), ask `exists (select 1 from work_item w where w.id = <item> and (w.built_ins_as_arrived is null or app.holds_work_item(w.id)))`. A policy written `<item> in (select id from work_item)` checks every item in the database each statement, every Company's: never write one.
   - The work item query (the List, Kanban, Export, Dashboard, Package page, Home and the Projects page's Submittals counts) reads its rows from `app.work_items_seen(project, modules, all revisions, item ids)`: the scope's items the caller sees (or only the ids given, their Revision chains still read whole), each checked once, with what `app.step_as_seen`, `app.work_item_holder`, `app.work_item_creation_date`, `app.with_owner_review`, `app.latest_visible_revision` and `app.revision_chain` give for each, the Trade and Location as `work_item_dimension_value_seen` gives them, and the holder's and raiser's Company names (`app.work_item_companies`). It reads the last five for many items at once, so seam-2 `work-items-seen.test.ts` checks it says what those functions say, for every Member and item in the test database. The api reads it once per transaction into a temporary table dropped at commit; only reads use it (a Package page reads its few items directly).
   - `app.step_as_seen`, `app.work_item_holder`, `app.work_item_creation_date` and `app.with_owner_review` check the item, then run their `<name>_unchecked(item, participant ids)` body, which no role but the migrator may run: `app.work_items_seen` calls those for items it has checked. A rule is written once, in the unchecked body.
   - `app.work_items_waiting_on_me(projects)`: the items `app.need_my_action` says wait on the caller, the latest Revision of each chain they see, from their own Participants' open assignments (the Projects page's Need My Action count and Home's list).
   - `apps/api/test/reads-at-scale.test.ts` reads Home, the Submittals List and Kanban and the Snag List of a Project of 2,500 items within a bound.

## Settled points

- **Oversight:** Owner and Owner Representative get access at first Submit, within their Visibility (`reason = oversight`). See docs/visibility.md V2.
- **Informed:** a Submit may name roles to inform; their covering Participants get access at that Submit (`reason = informed`, RP-625), read-only. See docs/visibility.md V2.
- **Snags assigned to a Contractor:** the Contractor sees the shared history only, never the raiser's internal events (V5).
- **Search:** Postgres full-text search first, always filtered through RLS. As built (RP-347): `work_item_search`, one row per Work Item kept by triggers, holds the Document Number, Subject, Type name, Trade and Location names and the raiser's Company name (English and Arabic), never answers or Documents, with a trigram and a full-text index. The app role can't read it; the List's `q` finds items through `app.search_work_items(project, q)`, which returns only the ids of matching items the caller sees. Every word must match: one of three letters or more as a part of a word, a shorter one as a whole word. A search's Stage counts are of the List's page, or the Kanban's shown cards, only.
